# Derive an auditable greenfield exporter requirements baseline

## Signal

The Obsidian plugin rejects the exporter bridge because it requires schema version 2 while the current exporter emits schema version 3, blocking note preparation. The existing exporter implementation is too large and entangled to serve as a maintainable implementation base, yet its repository contains the only current behavioral evidence for the publication pipeline.

## Problem Type

synthesis

## Constraints

- Do not refactor or treat exporter-java implementation structure as the greenfield architecture.
- Infer functional requirements from current production code, tests, documentation, scripts, fixtures, plugin integration, site integration, and active Haft decisions.
- Express canonical requirements as coarse-grained OpenSpec capabilities with normative Given-When-Then scenarios.
- Separate observed current behavior, binding requirements, historical migration behavior, and unresolved decisions.
- Preserve explicit human approval as the only boundary that advances the approved publication baseline.
- Apply the named FPF skill to audit completeness, unambiguity, cohesiveness, strict distinctions, scope, and evidence traceability.
- Do not implement the new exporter in this work slice.

## Optimization Targets

- High behavioral coverage with direct evidence traceability.
- Small cohesive capability boundaries suitable for acceptance testing and clean OOP design.
- Unambiguous normative language that lesser-context agents can consume independently.

## Observation Indicators

- Number of legacy behaviors that remain evidence-backed but are deliberately excluded from the greenfield core.
- Number of unresolved product decisions that cannot be inferred safely from repository evidence.

## Acceptance

Canonical OpenSpec spec files exist for every derived coarse-grained exporter capability; every requirement has at least one Given-When-Then scenario and source evidence; a separate FPF audit evaluates completeness, ambiguity, cohesion, and strictness and records unresolved gaps; OpenSpec validation, Haft structural checks, and repository whitespace checks pass; no exporter or plugin production code is changed.

## Blast Radius

Requirements and governance carriers under openspec/ and .haft/ only; exporter-java, obsidian-plugin, site, vault, review workspaces, and publication baselines remain read-only evidence sources.
