# S19 — Stable semantic occurrence map

## Signal

SEM-02 and TRP-05 are unimplemented: `prepare` has no notion of a semantic occurrence map, so nothing today assigns or preserves stable occurrence IDs/order across RU, EN, and references.json, and nothing rejects a translation-worker result that reorders or invents occurrences relative to the referrer's real link set.

## Problem Profile

thin

## P2W Readiness

p2w_blocked

## Why Now

User directed implementation of slice S19 now, following the already-closed S18 problem (prob-20260814-9d502f85), continuing the plan's strict sequential slice order.

## Scope

One in-memory referrer publication and one in-memory target publication, plus a previous occurrence map fixture for the map-reuse scenario. Requirements introduced: SEM-02 (stable occurrence IDs and order across RU/EN/references.json), SEM-03 non-empty-map case (SEM-03 empty-map case was already covered in S03/S05), TRP-05 (translation-worker map validation: reject reordered or invented occurrences). Codec-level unit tests are justified only for genuinely combinatorial references.json parsing: duplicate keys, hash stability, strict number/order parsing. Explicitly excluded per the plan: resolving an occurrence into a public route at release time (that is S20's late-bound target activation).

## Acceptance

A failing system-boundary acceptance test (Given-When-Then) drives: preparing a linked publication produces RU, EN, and references.json sharing identical stable occurrence IDs and identical order; a worker result that reorders or invents occurrences relative to the referrer's real link set is rejected before candidate replacement. Whole prior acceptance suite stays green. In-memory acceptance subset stays under one second. At most one new production boundary adapter is introduced only if genuinely required (the plan expects this slice to stay in-memory/codec-level, per its acceptance boundary).

## Blast Radius

Local to publication-exporter's prepare/translation-validation path; no site or release-tree changes in this slice.

## Reversibility

Reversible — new behavior lands as one reviewable commit on master with full test coverage; no migration or irreversible external effects.
