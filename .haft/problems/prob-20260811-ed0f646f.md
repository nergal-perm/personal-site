# S14 — Content-addressed assets (PCM-05)

## Signal

LinkResolver (publication-exporter/src/main/java/.../prepare/LinkResolver.java) already classifies an embed target as asset-like by extension (ASSET_EXTENSIONS) but explicitly leaves it untouched: `appendLink` does `output.append(link.group())` and returns without blocking, verbatim-copying the raw `![[image.png]]` Obsidian embed syntax into the normalized candidate body. PCM-05 (openspec/specs/public-content-model/spec.md) requires the exporter to resolve referenced publishable assets within the vault (preferring an exact vault-relative match over a unique basename fallback), reject ambiguous/unsafe (traversal/symlink-escaping) targets before any candidate replacement, and materialize each accepted asset under a deterministic content-derived (hash) name so identical bytes referenced more than once collapse to one public asset. None of this exists yet: VaultReader (vault/VaultReader.java) exposes only readSource/exists/listPublishCandidates for note text — no binary asset read capability — and CandidateWorkspace (candidate/CandidateWorkspace.java) has no notion of installing an asset alongside RU/EN bodies. exporter-java's AssetResolver (astroexport/assets/AssetResolver.java) was read as behavioural evidence only (compatibility oracle, not a code donor): SHA-256 content-addressing, exact-path-before-basename-fallback, ambiguous-basename rejection, traversal/symlink/hidden-path escape rejection, and byte-identical dedup with suffix-family consistency checking.

## Constraints

- At most one new production boundary adapter: asset byte reading + content-addressed materialization.
- No asset variants, optimization, remote assets, or media types beyond the existing ASSET_EXTENSIONS set (png/jpg/jpeg/gif/svg/webp/mp3/mp4).
- In-process acceptance subset stays below one second.
- One to three new OpenSpec scenarios targeted (PCM-05's three baselined scenarios).
- exporter-java remains a read-only compatibility oracle, never a code donor.
- No candidate/approved/release state change in one unreviewable step.

## Acceptance

Preparing an essay with one image emits one content-addressed asset and rewrites the candidate reference to point at it; an ambiguous basename match or an escaping/unsafe target (traversal, symlink) blocks preparation with an asset diagnostic before any candidate replacement; identical asset bytes referenced more than once materialize as exactly one deterministic public asset with all references pointing at it. In-memory asset bytes prove the behaviour first; a real vault/file adapter then passes the same exact-path, ambiguous-basename, deduplication, and escape contracts.

## Blast Radius

publication-exporter prepare pipeline (LinkResolver call site in PrepareHandler), a new asset-resolution collaborator, VaultReader (or a sibling asset-reading capability), CandidateWorkspace (asset materialization alongside RU/EN bodies). No change to exporter-java, obsidian-plugin, bridge-contract schema shape, site/, approved-snapshot or release-materialization code paths, or any other content kind.
