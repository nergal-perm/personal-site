# S12 — Protected Markdown and Obsidian comments

## Signal

publication-exporter's prepare pipeline (PrepareHandler) installs the Russian candidate body verbatim from the admitted source, with no Markdown normalization step. PCM-04 (openspec/specs/public-content-model/spec.md) requires that Obsidian-only comment syntax (%%...%%) be removed from publishable prose while code, inline code, and other declared protected regions are left semantically unchanged — including any link-like, wiki-link, or embed-like text that happens to sit inside those protected regions, which must survive byte-for-byte. Neither requirement is implemented yet: PCM-04 is unimplemented in the new exporter (S01-S11 never touched Markdown content, only frontmatter/identity/workflow). The legacy exporter-java's MarkdownScanner class and MarkdownNormalizationTest are evidence/oracle only per this project's standing rule (CLAUDE.md, implementation-plan.md preamble) — not a design template or code donor for publication-exporter.

## Constraints

- Governed by openspec/implementation-plan.md's slice discipline: one failing system-boundary acceptance test in, one visible result out, at most 1-3 new OpenSpec scenarios, at most one new production boundary adapter (S12 needs none — pure in-process transform), in-memory acceptance subset under 1 second
- Explicitly excludes resolving actual links, transclusions, and assets (S13/S14's scope)
- exporter-java's MarkdownScanner/MarkdownNormalizationTest are evidence/oracle only, not a code donor — no direct port of its class or package structure into publication-exporter
- Governed by /nullables, /applying-sbpp, /elegant-objects, /oo-design-guide per this project's standing convention for exporter code
- The acceptance boundary is one fixture through prepare; narrow unit tests only if the scanner has genuinely combinatorial protected-region cases

## Acceptance

Preparing an essay whose Russian source contains an Obsidian comment produces a candidate with that comment absent from public content; preparing an essay whose source contains link-like, wiki-link, or embed-like text inside a fenced code block or inline code span produces a candidate where that protected text is byte-for-byte unchanged. Both scenarios pass through the real `prepare` CLI/handler path (PCM-04's two baselined scenarios in openspec/specs/public-content-model/spec.md), and the full acceptance suite (currently 484 publication-exporter tests) stays green.

## Blast Radius

publication-exporter's prepare package (new Markdown-normalization collaborator plus its call site in PrepareHandler); no schema-v2, CLI surface, or other handler changes expected
