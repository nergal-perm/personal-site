# S11 — Truthful workflow state and queue refresh

## Signal

The exporter has four working bridge commands (prepare, inspect-publication, mark-reviewed, build-from-review, install-to-site) but no refresh-publication-queue: Main.java's subcommands list does not include it, and no frontmatter workflow scalar is ever persisted back to a source note anywhere in the codebase (grep for workflow/publication_status/status_ keys in src/main returns nothing). InspectPublicationHandler and BridgeResponse already compute and return the six-state vocabulary (metadata_blocked, ready_for_review, translation_failed, ready_to_publish, stale — translating not yet observed anywhere) live, per-note, on demand, but nothing writes that classification back to disk or reconciles it across a set of tracked publications. BRG-01's refresh clause, BRG-05, and BRG-06 (workflow-bridge/spec.md) and TRP-06 (translation-preparation/spec.md) are already fully specified with scenarios, which is evidence this is primarily a realization slice — but that must be confirmed via the functional collaborative-design pass, not assumed. S08's PrepareHandler holds an in-process ReentrantLock keyed by PublicationIdentity only for the duration of one synchronous prepare() call, so it does not by itself give a later, separate refresh process any durable signal that a translation is active; how refresh detects 'actively translating' needs a technical design decision, not a guess.

## Problem Type

synthesis

## Constraints

- No unrelated frontmatter normalization or whole-file YAML rewriting — implementation-plan.md explicitly excludes this from S11
- At most one new production boundary adapter (implementation-plan.md slice rule) — a guarded exporter-owned frontmatter workflow-scalar editor; reuse the existing Frontmatter/FrontmatterScalar parser rather than introducing a new YAML engine
- Reuse the six-state classification already computed by InspectPublicationHandler/BridgeResponse rather than reinventing a second classifier that could disagree with inspect-publication for the same observation window (BRG-05's 'same command, same state' scenario)
- Queue refresh scans publication candidates already known to the exporter, not a whole-vault discovery pass — ADM-01/whole-vault discovery is S16's job, not this slice's
- Do not touch prepare, inspect-publication, mark-reviewed, build-from-review, or install-to-site business logic itself
- In-memory acceptance test subset first (decisive/uncertain/translating vault fixtures), then the same contract against the real frontmatter editor for byte/permission preservation

## Acceptance

refresh-publication-queue reports updated/unchanged/uncertain counts across the six-state workflow vocabulary and updates only stale exporter-owned workflow scalar fields via a guarded atomic replacement that preserves all other source bytes and file permissions. A note whose persisted workflow scalar decisively disagrees with its unambiguous current artefact state is corrected and counted as updated. A note under an active, valid translation lock is left untouched (workflow state and job ownership not overwritten) and does not count as updated. A note whose source changed concurrently since validation, or whose workflow keys are duplicate/aliased/malformed, blocks the update without rewriting the source and is counted as uncertain rather than guessed. All existing acceptance/unit tests remain green plus new S11 acceptance coverage: an in-memory vault with decisive, uncertain, and translating fixtures proves the reconciliation contract, then the identical contract runs against the real frontmatter editor.

## Blast Radius

publication-exporter: new refresh-publication-queue command/handler, a new guarded frontmatter workflow-scalar editor port + Filesystem/in-memory adapters, and (if the functional design pass confirms it) extraction of the existing six-state classification logic out of InspectPublicationHandler so refresh and inspect-publication share one classifier. Does not touch prepare, mark-reviewed, build-from-review, install-to-site business logic, whole-vault discovery (S16), additional content kinds (S17+), or semantic references (S18-S20).
