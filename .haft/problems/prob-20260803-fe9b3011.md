# Sequence the greenfield exporter as minimal visible vertical slices

## Signal

The requirements baseline is complete, but implementing capabilities one by one would create large horizontal batches and long periods with no usable exporter behavior. The implementation needs a dependency-aware sequence in which every small increment produces a visible CLI, plugin, review-workspace, or site-output result.

## Problem Type

synthesis

## Constraints

- Each implementation slice begins with a failing system-boundary acceptance test and ends with observable exporter behavior.
- Keep the daily acceptance loop in-process and sub-second using in-memory adapters; add real I/O only behind behavior-proven contracts.
- Do not reproduce exporter-java classes or package structure.
- Start with one simple publication kind and one note; defer additional kinds, links, assets, queue refresh, migration, and native packaging until their own slices.
- Never weaken approval authority, path safety, candidate versus approved separation, or fail-closed bridge schema v2 behavior.
- Each slice names included OpenSpec scenarios and explicit exclusions; no foundation-only or refactoring-only slices.
- The plan is high-level and technology-neutral until the residual language, project-folder, bridge-carrier, translation-protocol, cutover, and distribution decisions are recorded.

## Optimization Targets

- Shortest time to a working single-note publication path.
- Minimum independently reviewable change per slice.
- Sub-second executable acceptance feedback.

## Observation Indicators

- Number of requirements pulled into a slice only because of speculative reuse.
- Acceptance runtime and number of real-I/O tests.
- Slices that lack a user-visible command, response, review artifact, or site artifact.

## Acceptance

A committed plan maps every one of the 47 requirements to a dependency-ordered implementation slice or an explicit conditional/deferred gate; every slice has one visible result, a minimal acceptance boundary, exclusions, and an outside-in test approach; the first path restores one real publication kind end-to-end before breadth is added.

## Blast Radius

Planning and governance carriers only under openspec/ and .haft/; no exporter, plugin, site, vault, or review-workspace production changes.

**Parity plan:**
- Baseline set: 47 OpenSpec requirements, 101 Given-When-Then scenarios, one blog/essay first-use path
- Window: planning snapshot 2026-08-03
- Budget: one independently reviewable commit per slice; sub-second in-memory acceptance subset
- Missing data policy: explicit_abstain
- Normalize new acceptance scenarios per slice with raw count
- Normalize new production boundary adapters per slice with raw count
- Normalize observable result with binary pass when at least one coherent boundary result exists
- Normalize fast acceptance runtime with milliseconds
- Pinned condition: Bridge schema major v2
- Pinned condition: Explicit approval is sole approved-baseline writer
- Pinned condition: Candidate, approved snapshot, and release projection stay distinct
- Pinned condition: No existing exporter implementation structure is reused as architecture
- Pinned condition: Compare proposed sequences against the same 47-requirement baseline and the same first usable outcome: one blog/essay can travel from plugin-compatible command through explicit approval to generated site input. No sequence may count test-only plumbing or an internal abstraction as a visible result.
