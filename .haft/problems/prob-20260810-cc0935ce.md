# S13: Public/private links and transclusion safety in prepare

## Signal

Preparing an essay currently ignores link-like syntax entirely — S12 only strips Obsidian comments while protecting link-like syntax inside code regions. There is no resolution of internal wikilinks/transclusions against vault topology, so a public link, a private/unresolved link, and a private transclusion are all emitted unchanged (or worse, could leak absolute vault paths) into the candidate.

## Constraints

- Requirement PCM-03 only; do not implement stable semantic occurrence IDs (SEM-02) or late-bound target activation (SEM-04/05) — those are S19/S20
- Link resolution stays in-process (no new production adapter) until real vault lookup behaviour has emerged, per implementation-plan.md S13 acceptance boundary
- Must not leak vault topology (absolute paths, internal note IDs) through blocked/private link labels
- One to three new OpenSpec scenarios per slice discipline
- In-memory acceptance subset must stay under 1 second
- Whole prior acceptance suite must remain green

## Acceptance

A three-note in-memory vault acceptance test shows: (1) one unambiguous link to a publicly-admitted note is converted to its public route, (2) one link to a private or unresolvable target renders as a safe plain-text label with no leaked path/route, (3) one private transclusion is blocked before candidate replacement rather than being inlined or silently dropped. PCM-03 requirement is satisfied. Full suite stays green; no new production adapter beyond in-process resolution (real vault lookup deferred per plan).

## Blast Radius

publication-exporter prepare pipeline (PrepareHandler and the Markdown normalization path introduced in S12); candidate content shape consumed downstream by review/approval/release, though this slice does not touch those stages
