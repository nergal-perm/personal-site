The live site already models `concepts` as a real public collection: site/src/content.config.ts defines the concepts schema (title, description, editorial/translation fields, plus notThis: optional string, relations: {name, relation}[] default [], examples: string[] default []), site/src/pages/{ru,en}/concepts/[id].astro publishes it, and ConceptPage.astro renders notThis as a translated boundary callout and relations/examples as translated prose lists. The current exporter's PublicationKinds.installed() does not register concepts/concept, so it is blocked at kind lookup.

Unlike book's authors (invariant scalar list, S17c) or claim's supports/opposes (invariant structured list with a target link, S17b), concept's notThis/relations/examples are user-facing prose meant to be translated RU->EN, not invariant metadata. The current PublicField carrier only holds an ordered list of scalar translated key-value pairs; there is no existing carrier for a translated list of scalars or a translated list of structured objects. This is the one genuine technical gap this slice must resolve or explicitly defer (mirroring S17c's precedent of hard-blocking bibliography/book's selectedQuote rather than silently mistranslating or copying Russian prose into English candidates).

## Resolution

Addressed via openspec/changes/archive/2026-08-12-s17d-concepts-concept-kind/. Resolved the translated-list gap by extending translation (Option A from collaborative design): `ConceptPublicationKind` flattens `relations`/`examples` into synthetic-keyed `PublicField` entries at admission, reusing the existing translation pipeline unmodified; `BracketIndexedFields` (new, generic, kind-agnostic) reassembles them into YAML list structure at site-install time. `FieldContract` gained a `STRUCTURED_LIST` type for `relations`' `{name, relation}` shape. Implemented via subagent-driven-development (4 tasks, Codex Companion Tasks: Spark/Luna/Sol tiers), per-task 4-way parallel review with fix loops, and a final whole-branch review (GPT 5.6 Sol, xhigh effort) that caught and the controller fixed a real runtime/contract disagreement for optional empty/malformed list fields. Full suite green (728/728, `mvn -f publication-exporter/pom.xml test`). 16 commits on master since baseline 6e8affd.

# S17d — concepts/concept kind and translated-list projection (ADM-03, ADM-04, PCM-02, PCM-06)

## Signal

Whole-vault admission and the publication contract cannot cover concepts/concept; no concept note can travel through prepare -> approve -> release -> site install, and write-publication-contract omits the kind entirely, even though the live site already serves two concept fixtures (org-3-0, structural-shifts-of-increased-productivity) with real content.

## Problem Profile

thin

## P2W Readiness

p2w_blocked

## Scope

publication-exporter/src/main/java/dev/eugene/publicationexporter/{admission,contract,reference,prepare,translation,site}/ and matching test packages. No changes to exporter-java/ (evidence-only) or to site/ (already-shipped schema/views, evidence-only for this slice).

## Acceptance

One concepts/concept fixture completes admit -> prepare -> approve -> build-from-review -> install-to-site through the real CLI, matching the S17a-S17c slice shape (implementation-plan.md S17a-S17f). write-publication-contract includes the concepts/concept kind with deterministic field ordering. The translated-vs-invariant posture of notThis/relations/examples is explicitly decided (not silently guessed) and, if any of them are blocked/deferred in this slice, that limitation is explicit in admission diagnostics and the contract, not a silent data-loss path. Existing blog/bibliography kind acceptance suites remain green; mvn -f publication-exporter/pom.xml test passes.

## Blast Radius

One new PublicationKind implementation plus, if the translated-list gap is closed, a bounded extension to the PublicField/translation carrier shared by every kind. No irreversible migration or external state change; plain git revert rolls back.

## Reversibility

reversible
