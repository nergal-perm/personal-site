# Cross-kind (collection, publicId) address collision across candidate/approved/release/site adapters

## Signal

Every real filesystem adapter in publication-exporter keys its on-disk path by (publicCollection, publicId) only, never publicContentType: FilesystemCandidateWorkspace (candidate/FilesystemCandidateWorkspace.java:167-169, resolves `{collection}/{publicId}/candidate`), FilesystemApprovedSnapshotWorkspace (approved/FilesystemApprovedSnapshotWorkspace.java:445-447, `{collection}/{publicId}/approved`), FilesystemReleaseOutputStore (release/FilesystemReleaseOutputStore.java:54-58, `{collection}/{publicId}/release`), and FilesystemManagedSiteInstaller (site/FilesystemManagedSiteInstaller.java:383-386, `src/content/{collection}/{locale}/{publicId}.md`). PublicationIdentity's own equality (bridge/PublicationIdentity.java) is (collection, contentType, publicId) — so two admitted publications of different kinds sharing the same collection and publicId are treated as distinct by admission, but resolve to the identical real path in all four adapters. This was unreachable before S17a because blog/essay was the only kind ever admitted into the "blog" collection; S17a (prob-20260811-ab6a410a) added blog/note as a second real kind sharing that same collection, making the collision reachable for the first time: a `blog/essay/foo` and a `blog/note/foo` would silently overwrite each other's candidate, approved snapshot, release output, and site-content file. PublicationManifestHandler (manifest/PublicationManifestHandler.java, the ADM-05 whole-vault handler) performs no cross-note duplicate-identity detection at all, for any kind pair, so nothing in the current system would surface this before the collision actually happens on disk. S17a's final whole-branch review (gpt-5.6-sol, xhigh effort) surfaced this; the operator elected to track it as its own problem rather than patch it inside S17a's fix wave, since S17b-S17f (openspec/implementation-plan.md's remaining content-kind ladder) will all share the "blog" collection too and are equally exposed.

## Problem Profile

thin

## P2W Readiness

p2w_candidate

## Why Now

Surfaced by S17a's (prob-20260811-ab6a410a) final whole-branch review as the first real cross-kind collision now that a second kind shares a collection; must be resolved before S17b (blog/claim) makes it a three-kind exposure.

## Scope

publication-pipeline

## Constraints

- Must not require re-laying-out the on-disk structure of already-approved/released essay data without a safe migration path — any fix touching real adapter paths needs to handle publications that already exist under the current (collection, publicId)-only layout
- Should not require a new production boundary adapter merely to add a check — prefer extending an existing adapter/handler's own invariant over introducing new I/O surface
- Must resolve before S17b (blog/claim) lands, since claim shares the "blog" collection with both essay and note and would be exposed to the identical collision the moment it exists

## Optimization Targets

- No two admitted publications of different kinds sharing a collection and publicId can silently overwrite each other's candidate, approved snapshot, release output, or site content
- Preserve today's real on-disk layout for already-approved/released publications unless a decision explicitly authorizes a migration

## Acceptance

A decision or slice exists that either (a) makes (collection, publicId) uniqueness an enforced invariant across kinds at admission or install time (fail closed on a second kind claiming an already-used publicId within the same collection), or (b) extends the real adapters' addressing to include contentType with an explicit, evidence-based migration story for already-approved essay data. Either way, a reproduced fixture proving a blog/essay/{slug} and a blog/note/{slug} no longer silently collide on disk is part of the acceptance evidence.

## Blast Radius

candidate/FilesystemCandidateWorkspace.java, approved/FilesystemApprovedSnapshotWorkspace.java, release/FilesystemReleaseOutputStore.java, site/FilesystemManagedSiteInstaller.java, and/or manifest/PublicationManifestHandler.java, depending on which resolution is selected. Affects every future S17b-S17f content-kind slice sharing the "blog" collection.
