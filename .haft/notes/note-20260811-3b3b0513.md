# FilesystemVaultReader's TOCTOU pathname-swap gap (previously flagged) is now fixed

## Observations

- note-20260811-7c3fbc10 flagged that FilesystemVaultReader.listPublishCandidates() had the same TOCTOU pathname-swap shape S14's Task 6 fixed in FilesystemVaultAssetReader.
- S16's final whole-branch review independently re-confirmed this gap and it was fixed in commit 36dc92e: hasPublishTrueFlag now reads through the confinement-validated real path (via a new private ConfinedCandidate(originalPath, realPath) record) instead of re-reading via the original unresolved path.
- FilesystemVaultReader now also carries the same threat-model Javadoc FilesystemVaultAssetReader already had, documenting the accepted residual TOCTOU window (path-based APIs cannot provide descriptor-anchored opening; this project's threat model is a single local user exporting their own vault, not concurrent adversarial writes).
- A new regression test (listPublishCandidatesDiscoversASelectedNoteReachedThroughASymlinkInsideTheVault) proves the non-racy part of the fix: a selected note reached through an in-vault symlink is still discovered under the symlink's own vault-relative path.

## Rationale

Closes the loop on a previously-recorded gap so a future session doesn't re-flag it as still-open; the fix and its precedent are now both in the codebase and in the graph.
