# FilesystemCandidateWorkspace.requireDirectChild runs after path normalization, so a publicName with '..' segments that still resolves within assets/ is accepted as an alias

## Observations

- writeAssets() resolves each CandidateAsset.publicName() via candidateFile(assetsDirectory, publicName), which calls Path.resolve(...).normalize() BEFORE requireDirectChild() checks the parent directory.
- A publicName like 'x/../hash.png' normalizes to 'assets/hash.png' before the check runs, so it passes requireDirectChild (parent is exactly assetsDirectory) even though it contains a path separator.
- Three independent Codex reviewers (quality, sbpp, oo-design) confirmed this does NOT reopen the path-traversal/overwrite-escape vulnerability fixed in S14 Task 7 (commit 15a79ce) — normalization always collapses such a name to a location still confined within assets/. The only consequence is that two differently-spelled publicName values could alias the same real file.
- Today's only real caller (AssetResolver) always produces a flat sha256-hex-plus-extension publicName with no separators, so this is not currently reachable through the shipped pipeline — same class of latent-but-unreachable gap as the TOCTOU finding in Task 6.

## Rationale

Recorded so a future decision can weigh whether to validate publicName as a single path element BEFORE resolution (ideally in CandidateAsset itself, per oo-design's suggestion) rather than relying on normalize()-then-confine. Low urgency: no security impact, current caller is safe, purely a semantic-cleanliness gap in a general-purpose collaborator.
