# S17e Task 3 parked findings: containment-style assertions and disconnected workflow-editor wiring match S17d precedent

## Observations

- Code-quality review: AlbumAcceptanceTest's translated-field assertions use installedRu.contains(...)/installedEn.contains(...) (loose substring match) rather than exact-equality assertEquals on the full translated block, unlike the invariant block which IS checked with exact equality. Verified: ConceptAcceptanceTest.java line 117 uses the identical installedRu.contains(...) pattern for its own translated fields, already shipped and SHIP-verdicted in S17d's final review with no such finding raised there.
- OO-design review: AlbumAcceptanceTest constructs a real, path-configured NullWorkflowStatusEditor but passes a separate, unconfigured WorkflowStatusEditor.createNull() to PrepareHandler -- the configured editor is only exercised by the later MarkReviewedHandler call, so PrepareHandler's own workflow-write collaboration is never exercised with real data in this test. Verified: ConceptAcceptanceTest.java line 87 does the exact same thing (WorkflowStatusEditor.createNull() passed to PrepareHandler, the configured editor reserved for MarkReviewedHandler only) -- an already-shipped, SHIP-verdicted S17d pattern, not something album's implementer introduced.
- Both patterns appear to be copied verbatim across every XyzAcceptanceTest file in this codebase (book/claim likely share them too, not individually re-verified here), suggesting a cross-cutting convention rather than a per-slice choice -- worth revisiting in a future dedicated cleanup pass across all acceptance tests at once, not piecemeal per new kind.

## Rationale

Fixing either pattern only in album's test would create asymmetric rigor relative to every already-shipped sibling acceptance test and implicitly demand a retroactive fix to S17d's already-approved code, which is out of this slice's scope. Parked with ruling rather than fixed.
