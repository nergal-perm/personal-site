# Approval must persist workflowStatus and later inspection must recognize the matching approved candidate

## Observations

- The initial live approval returned `ready_to_publish` while leaving the source note's `workflowStatus` unchanged. The operator could see an approval result that the source note did not durably reflect.
- `MarkReviewedHandler` now writes only `workflowStatus: ready_to_publish`, guarded by the source hash used for approval, after the approved snapshot is installed. A failed status write returns a blocked bridge response rather than claiming successful approval.
- `InspectPublicationHandler` now treats a candidate identical to its approved snapshot as `ready_to_publish`, with no review plan. `RefreshPublicationQueueHandler` uses the same distinction so queue reconciliation does not regress that note to `ready_for_review`.
- The real pilot note `blog/Фрактальность TDD.md` was subsequently observed with `workflowStatus: ready_to_publish`. Its older `publicWorkflow*` and `publicTranslationStatus` fields were retained; this session did not migrate or delete legacy frontmatter.

## Rationale

The source workflow scalar is the operator-visible record of the approval boundary. It must agree with the durable approved snapshot, while a byte-preserving one-scalar edit avoids incidental vault-frontmatter migration. Legacy-field removal remains a separate cutover decision, not a side effect of one pilot.
