# PrepareHandler's stale re-read can crash on genuinely malformed frontmatter injected mid-translation

## Observations

- S11's scoped re-review of the final-review fix wave (Codex gpt-5.6-sol xhigh) found a NEW Important issue introduced by commit 8662093's fix for the stale-hash finding: PrepareHandler.recordStaleWorkflowStatus re-reads the CURRENT source to compute the guard hash, but if the note was corrupted to invalid/absent frontmatter (not just changed) during the translation window, that malformed content's hash matches at write time, so FilesystemWorkflowStatusEditor.write() proceeds to Frontmatter.parse(...).withScalarSet(...) — whose closingDelimiterLineIndex() throws IllegalStateException on missing frontmatter (originally documented as safe fail-fast since every prior call site was guaranteed post-NoteIntake-validated content; this new re-read breaks that guarantee).
- recordStaleWorkflowStatus only catches UncheckedIOException/NoSuchElementException (for a vanished file), not this IllegalStateException, so it propagates uncaught out of prepare(), crashing the CLI invocation instead of returning the structured `stale` BridgeResponse.
- Judged non-load-bearing and parked, not fixed in a third round: requires a narrow, adversarial-timing trigger (frontmatter must be corrupted specifically DURING an in-flight translation, not just changed), and even when triggered causes no data corruption — no candidate is installed, workflowStatus simply stays unwritten (the same practical outcome as an ordinary blocked/hash-mismatch write, just via an uncaught exception instead of a graceful path). Symmetric in kind to the already-deferred UNCHANGED-shortcut TOCTOU note and BRG-06's documented mid-translation operational assumption.
- If revisited: catch IllegalStateException (or broaden to RuntimeException, matching RefreshPublicationQueueHandler's finding-6 pattern) in recordStaleWorkflowStatus's try/catch alongside the existing UncheckedIOException/NoSuchElementException.

## Rationale

Adjudicated per the SDD final-review breaker rule (no second fix wave; park non-load-bearing residuals surfaced by the fix diff itself) — narrow trigger, no persisted-state corruption, and the fix that introduced it (deriving the guard hash from current content) correctly resolved the original, more consequential finding (stale could never persist at all).
