# Russian translation source is an unnamed body-title-description tuple

## Observations

- TranslationOutcome.resolve(Function<EnglishTranslation,T>, Function<TranslationFailure,T>) does not accept Russian text and correctly dispatches successful and failed outcomes.
- TranslationWorker, ProcessTranslationWorker, TranslationJob.forSource, and PrepareHandler repeatedly pass the same Russian body, title, and description as separate String parameters.
- TranslationJob currently validates and fingerprints that tuple although it does not model the source value from which the fingerprint is derived.
- EnglishTranslation has the same three-field shape but represents translated output; it should not be generalized with the Russian source solely for structural reuse.

## Rationale

The repeated primitive tuple obscures a cohesive source concept, scatters its invariants and fingerprinting, and makes translation-layer collaboration parameter-heavy. A future refactoring should introduce an immutable domain-specific RussianSource value, use it at the job and worker boundaries, and retain TranslationOutcome.resolve unchanged.

## Source

Elegant Objects: prefer an immutable whole value over an unnamed data clump. SBPP: the raw tuple mixes source-level intent with string mechanics, whereas resolve remains an appropriate dispatched interpretation. OO heuristics: related source data and its validation/fingerprint behavior are separated and passed through chatty collaborations.
