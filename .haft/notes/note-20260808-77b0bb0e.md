# RefreshPublicationQueueHandler duplicates NoteIntake's source read/hash instead of reusing intake.sourceHash()

## Observations

- S11 Task 9 oo-design-heuristics review (Codex gpt-5.6-terra, Riel 2.9/4.1) found that RefreshPublicationQueueHandler.reconcileOne reads, parses, and hashes the note's source itself via vaultReader.readSource + Frontmatter.parse + ContentHash.sha256Hex, then calls NoteIntake.admit(...) which reads/parses/hashes the same note again internally.
- NoteIntake.Result already retains the parsed Frontmatter and, since S11 Task 7's fix (commit eba008f), exposes sourceHash() computed once at admission time.
- Suggested fix: expose a narrow persisted-workflow-status query from accepted NoteIntake.Result, then use intake.sourceHash() for the guarded write in RefreshPublicationQueueHandler, removing its direct Frontmatter/ContentHash coupling.
- Deferred as Minor severity — not a correctness bug, a redundant-I/O and coupling cleanup opportunity. Parked, not fixed in commit 0c3ce8f.

## Rationale

The fix for Task 7's TOCTOU finding (carrying admission-time sourceHash forward) makes this duplication newly avoidable in Task 9's handler, but fixing it wasn't in Task 9's scope; worth revisiting together with NoteIntake.Result's shape next time either file changes.
