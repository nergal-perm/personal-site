# FilesystemVaultReader.listPublishCandidates() has the same TOCTOU pathname-swap shape S14's Task 6 fixed in FilesystemVaultAssetReader

## Observations

- In vault/FilesystemVaultReader.java's listPublishCandidates(), the stream filters each walked path via realPathOf(path).filter(isInsideVault).isPresent() (a boolean check that discards the resolved value), then hasPublishTrueFlag(path) reads file content via the ORIGINAL walked path, not the verified real path.
- This is the identical shape to a finding S14's Task 6 fix round 1 (commit 1150317) resolved in the new FilesystemVaultAssetReader: a concurrent filesystem mutation between the path-safety check and the content read could swap the verified location for a symlink pointing outside the vault.
- This pre-existing occurrence was explicitly left untouched during S14 Task 6's fix — the operator's plan scoped that fix to the new asset-reader adapter only; fixing FilesystemVaultReader was out of scope for that Haft problem.
- Three independent Codex reviewers (quality, sbpp, oo-design — oo-design at Critical severity) converged that this pattern should not be propagated into new security-sensitive code, even though it already exists here, unaddressed.

## Rationale

Recorded so a future decision can weigh whether to apply the same fix (collect/read via the resolved real path instead of the walked path) to FilesystemVaultReader, closing the same TOCTOU-style gap there. Given the project's actual threat model (single local user exporting their own vault, not concurrent adversarial mutation), this is low urgency but worth tracking rather than losing once this OpenSpec change archives.
