# Pre-existing staging-cleanup gap in FilesystemCandidateWorkspace/FilesystemApprovedSnapshotWorkspace

## Observations

- FilesystemCandidateWorkspace#install and FilesystemApprovedSnapshotWorkspace#install only clean up the staging directory on IOException; a RuntimeException from the post-mkdir requireWithinReviewRoot confinement recheck (a symlink-TOCTOU race) is not caught by that block, so the staging directory (with the written ru.md/en.md/references.json already inside it) is left orphaned on disk.
- This gap pre-dates S06 entirely -- it was present in the original S03/S04/S05 code and multiply reviewed without being caught. S06's Task 4 refactor (extracting StagedDirectoryInstall) faithfully preserved this exact behavior rather than introducing it.
- S06's final whole-branch review (gpt-5.6-sol) caught and fixed the identical gap in the new FilesystemReleaseOutputStore (commit 4c98892, try/catch/finally with an `installed` flag), but deliberately left the two pre-existing occurrences untouched -- fixing unrelated already-shipped code was ruled out of scope for closing out S06's own review findings.
- The consequence is low-severity (an orphaned staging directory on disk after a rare adversarial symlink race), not a confinement bypass or data corruption -- the ATOMIC_MOVE confinement check itself still correctly blocks the escape.

## Rationale

Recorded so a future slice (or a dedicated small cleanup slice) can fix all three Filesystem*Workspace/Store classes' install() methods consistently in one pass, rather than rediscovering this via another final review. Not fixed now because S06's own scope discipline (no speculative fixes to unrelated already-shipped code) argued against expanding the final-review fix wave beyond the new code that slice actually owns.
