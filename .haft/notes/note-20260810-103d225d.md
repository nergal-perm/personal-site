# S13 PublicNoteIndex snapshot can go stale between prepare()'s initial resolve and its post-translation freshness re-check

## Observations

- PrepareHandler.prepare() builds PublicNoteIndex once from the vault at call start and reuses that same snapshot inside sourceFreshness()'s post-translation re-check, rather than rebuilding it
- If a linked note's publish state changes (or a new ambiguous filename-stem collision appears) during the translation worker's synchronous call, the referrer's own candidate can still install with a route/label resolved against the now-stale snapshot
- Flagged as Important by the S13 final whole-branch review (gpt-5.6-sol, xhigh effort) as a PCM-03-relevant privacy concern
- Operator decision: defer to S20 rather than fix in S13 -- translateCandidate is a synchronous, blocking call (not queued/async job scheduling), so the exposure window is bounded to one worker call's wall-clock duration, not an open-ended race; this is architecturally closer to S20's late-bound target activation domain (target state changing independently of referrer processing) than to a bug in this slice's own scope
- Not implemented in S13; publication-exporter/src/main/java/dev/eugene/publicationexporter/prepare/PrepareHandler.java and PublicNoteIndex.java are the relevant files if S20's design needs to revisit this

## Rationale

Fixing this properly (rebuilding PublicNoteIndex a second time inside sourceFreshness, or re-verifying every resolved link's continued validity) would double the vault-enumeration cost on every prepare() call to close a narrow, bounded-duration race, for a concern that overlaps S20's already-planned late-bound-activation work. Deferring keeps S13 scoped to PCM-03's core requirement and avoids speculatively building consistency machinery before S20's actual design need is known.
