# Frontmatter.withScalarSet still mishandles an empty/comment-only existing value (residual of the S11 final-review fix)

## Observations

- S11's scoped re-review of the final-review fix wave (Codex gpt-5.6-sol xhigh) confirmed commit 8662093's surgical value-only replacement correctly handles quoted #, no-comment, and quoted-empty-string cases, but a line like `workflowStatus:    # keep` (empty value, comment-only) still has its comment treated as the value and deleted — valueStartOffset skips whitespace up to the #, and inlineCommentStart's `index > valueStart` guard fails to recognize that # as a comment start since it sits exactly at valueStart.
- Judged non-load-bearing and parked, not fixed in a third round: withScalarSet's only production caller writes workflowStatus with one of WorkflowState's ~7 defined non-empty constants (never an empty string), so this codebase never legitimately produces or preserves an empty-value existing line for the one key it actually rewrites. The gap only matters for a deliberately hand-edited empty/comment-only value, or a future caller of this general-purpose method with different value semantics.
- If withScalarSet gains a new caller that could plausibly encounter an empty existing value, revisit inlineCommentStart's boundary condition (currently `index > valueStart`) to also recognize a comment starting exactly at valueStart when preceded by only whitespace since the colon.

## Rationale

Adjudicated per the SDD final-review breaker rule (no second fix wave; park non-load-bearing residuals) — the practically-reachable byte-preservation cases (extra whitespace, trailing comment on a non-empty value) that motivated the original finding are fixed and tested; this narrower edge case doesn't threaten S11's actual usage.
