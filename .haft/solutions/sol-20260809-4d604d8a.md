# Solutions for: Antigravity prepare reports success without an English draft

Problem: prob-20260809-3e4c3d50

## Variants (3)

### V1. Approved-snapshot short-circuit bypasses Antigravity

Prime hypothesis. PrepareHandler returns an ok/ready response before TranslationWorker when the Russian source matches an approved snapshot. Live inspect-publication for blog/Фрактальность TDD.md reports ready_to_publish with candidateState=ready and approvedSnapshotState=ready; its review workspace contains both pairs. Thus the observed immediate success did not invoke agy.

**Novelty:** Workflow-state control flow rather than process execution.

**Weakest link:** Would be weakened if the user actually ran a different note without a matching approved snapshot.

### V2. Agy invocation contract fails to produce required files

Refuted as an explanation for an ok success. Agy supports the supplied flags, but even a zero-exit text-only run cannot produce BridgeResponse.prepared because ProcessTranslationWorker requires three files and otherwise returns translation_failed.

**Novelty:** External CLI/output-file contract rather than workflow state.

**Weakest link:** A future code change could bypass required-file validation, or a real controlled agy run could reveal an untested contract issue.

### V3. Plugin obscures bridge/process provenance

Supported contributing cause. Plugin treats any ok bridge response as a generic English-draft-ready notice; Java discards merged agent output and the plugin does not surface stderr. This makes an approved-snapshot shortcut indistinguishable from a fresh translation and makes real failures hard to diagnose.

**Novelty:** Observability and user-facing response provenance rather than decision logic.

**Weakest link:** Raw response/agent transcript from a future invocation could show that the user had enough separate UI context despite current code behavior.
