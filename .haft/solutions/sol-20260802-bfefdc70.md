# Solutions for: Wire up the real semantic link resolver end-to-end

Problem: prob-20260802-1803dd18

## Variants (5)

### V1. V1 Registry-first: initializer plus lazy per-note allocation inside Prepare

Follow the analysis doc's line literally. Add `init-semantic-site` that writes a valid activation marker (schemaVersion/inventorySha256/catalogSha256/activatedAt) with NO migration journal, plus an empty catalog — SemanticSchemaState.mode() returns SEMANTIC on marker-only, so this is reachable today. Semantic Prepare then reconciles ONLY the targets authored in the current note into VaultReferenceCatalog, writes it atomically, and installs the candidate triple. The 22 legacy pages are re-prepared one at a time through the ordinary Prepare path, with the existing approved EN used only as translation context.

**Strengths:**
- No new user-facing operation; the Obsidian workflow is unchanged
- Smallest catalog: only notes actually referenced by published pages ever get an identity
- Reuses SemanticReferencePlanner/PageReferenceMapCodec/ApprovedReleaseMaterializer untouched
- Cheapest to abandon if a rival wins

**Novelty:** The baseline rival: the recorded design direction taken literally, with identity allocation kept as a side effect of preparing a single page. It is the only variant that requires no new operation, no new bridge contract, and no vault-hygiene change — the minimum-new-concepts option, present so the others must beat something real.

**Weakest link:** Concurrency, not conversion. PrepareWorkflow.java:294 takes SemanticOperationLock.acquireShared for the entire Prepare. Lazy allocation makes Prepare a WRITER of catalog-v1.json while holding only a SHARED flock, so two concurrent Prepares both read the catalog, both allocate from the same max(vault-ref-NNNN), and VaultReferenceCatalog.writeAtomically's atomic exchange silently discards the loser — lost identity allocations, or two notes assigned the same vault-ref. That directly breaks hard constraint 6 (lock-guarded concurrency) and can break constraint 4 downstream. Upgrading to an exclusive lease for all of Prepare serializes the slowest operation in the workflow; upgrading mid-operation is a lock-upgrade deadlock. The doc's own admission that the failed-candidate recovery contract is undefined is the second-order symptom of this same coupling.

**Risks:**
- Shared-lease catalog writes lose allocations under concurrent Prepare (constraint 6)
- Recovery contract for identities allocated to a candidate that then fails is undefined by construction
- Allocation order depends on editing order, so vault-ref numbering is non-reproducible and diff-noisy
- A target only gains an identity when some referrer is prepared: a link authored to a not-yet-catalogued note degrades to plain text at Prepare time (SemanticReferencePlanner drops UNRESOLVED occurrences entirely), permanently losing that occurrence until the referrer is re-prepared — the exact late-binding failure the problem exists to fix

### V2. V2 Derived identity: targetRef is a pure function of the vault note, catalog demoted to a rename index

Stop allocating identities. Derive targetRef deterministically from vault-side data: `vault-ref-<sha256(frontmatter id, else normalized vault path)[0..16]>` — the scheme ReferenceMigrationInventory.provisionalPageRef already implements at line ~700. VaultReferenceCatalog stops being the authority for target EXISTENCE and becomes a pure rename/alias index consulted only to map a note's former path onto its earlier derived identity. VaultReferenceResolver gains a terminal layer that derives an identity for any resolvable vault path instead of returning UNRESOLVED. Prepare never has to write the catalog to make a link resolvable.

**Strengths:**
- No allocation means no atomicity/recovery/lock-upgrade design surface at all
- An unpublished, never-before-seen target resolves on first sight — late binding works from the first Prepare with zero prior state
- Reproducible: the same vault yields the same identities on any machine, making fixtures and the 22-page rehearsal exactly comparable to the real run
- Catalog corruption or loss stops being an identity-loss event

**Novelty:** Deletes an entire problem class rather than solving it: with content-addressed identity there is no allocation, so there is no allocation atomicity, no lock upgrade, no orphaned-identity recovery contract, and no ordering dependence. It also exposes a live inconsistency — the codebase ALREADY carries two incompatible targetRef schemes (numeric `vault-ref-%04d` from VaultReferenceCatalog.allocatePageRef vs. hex `vault-ref-<sha16>` from ReferenceMigrationInventory) and this variant is the only one that resolves the conflict by choosing rather than by keeping both.

**Weakest link:** Renames of notes that have no frontmatter `id`. A path-derived identity changes when the path changes, so an approved referrer's targetRef quietly stops matching and the link degrades to plain visible text forever — a SILENT failure (constraint 3 says identity must survive renames; nothing here blocks or even warns). The honest mitigation is mandating a frontmatter `id` on every note that may ever be a link target, which is a hygiene obligation across a 3549-note vault that the exporter cannot enforce and Obsidian will not maintain automatically. The rename index that patches this hole re-imports exactly the durable-state problem the variant claimed to delete, just in a smaller box.

**Risks:**
- Silent link decay on rename of id-less notes — fails soft, which is worse than failing loud here
- Requires reconciling two live targetRef formats already present in code, touching the migration path
- Pushes a vault-authoring convention (frontmatter id) into a system that currently demands none
- sha-truncated identities are opaque in diffs and unreadable during review

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Making the catalog non-authoritative means the review workspace stops being the sole custodian of semantic identity. That unlocks a future the other variants foreclose: an exporter that is stateless with respect to identity, a review/ tree that is fully reconstructible from vault + approved bytes after loss, and multi-machine or CI preparation without shipping a mutable registry between hosts. Even if the rename hazard disqualifies it as the final answer, building the derivation function is what makes catalog loss survivable under every other variant.

### V3. V3 Allocation as a separate idempotent operation over the publication frontier

Keep sequential registry identity, but stop making allocation a side effect of preparing a page. Add a distinct `reconcile-semantic-targets` operation that takes an EXCLUSIVE semantic lease, computes the publication frontier (every note reachable in one link hop from any `publish: true` note, derived from the discovery pass Prepare already runs), reconciles those descriptors into the catalog, and exits. Prepare keeps its shared lease and becomes a pure READER of the catalog again; if it meets an authored target with no identity, it BLOCKS with an actionable 'run reconcile' diagnostic rather than silently degrading the link. Init and reconcile are the same code path with an empty frontier.

**Strengths:**
- Restores constraint 6 cleanly: writers are exclusive, readers are shared, no upgrade
- Idempotent and re-runnable, so partial failure is not a recovery scenario
- Blocks instead of silently dropping an occurrence — makes the worst failure mode loud
- Bounded scan: the frontier is roughly 22 published notes plus their direct targets, not 3549 vault files
- Init is the degenerate case of reconcile, so one code path serves both instead of two

**Novelty:** Separates the two operations that V1 and the source doc fuse: identity allocation (a write, needs exclusivity, is idempotent and freely re-runnable) and candidate preparation (a read plus an atomic install). Once they are separate operations, the undefined recovery contract evaporates by construction — an identity allocated for a candidate that later fails is simply an unused active entry, which is legal and re-observable, not a corruption to recover from. It is also the only variant that turns 'target not yet catalogued' into a BLOCK instead of a silent occurrence loss.

**Weakest link:** The seam it introduces between authoring and preparing. Adding a link to a brand-new note now needs two operations, and the only way to keep the operator's one-button workflow intact is to auto-chain reconcile before Prepare — which re-fuses the two operations and drags the exclusive lease back into the Prepare path, restoring V1's concurrency problem with extra steps. The design lives or dies on whether the operator tolerates an occasional explicit second action; if not, this variant collapses into V1.

**Risks:**
- Two-step workflow contradicts the acceptance criterion 'no separate link-maintenance step' unless auto-chaining is accepted, and auto-chaining reintroduces the lock problem
- Frontier computation duplicates link parsing that SemanticReferencePlanner already does, and the two parsers must not diverge
- Catalog tombstoning churns whenever a frontier note is renamed or a link is removed
- An exclusive lease taken automatically can surface as a 'semantic operation is running' failure to the operator mid-edit

### V4. V4 Thick bridge: Obsidian owns the link graph, exporter validates and refuses

Move graph derivation to the process that already maintains it. The plugin uses metadataCache.resolvedLinks and getFileCache to compute, for the current note, the complete target descriptor set (path, heading, alias, label, frontmatter id) plus the inbound backlink set, and passes it to the exporter as a JSON payload over stdin (or a temp sidecar), bumping the bridge REQUEST contract alongside the existing response schemaVersion 2. The exporter re-reads the source bytes and rejects any descriptor it cannot confirm, but treats the plugin's set as the closure — no vault walk, no frontier computation. Backlinks feed a plugin-side 'referrers that will activate' queue shown when a target is published; the plugin never edits a referrer.

**Strengths:**
- No vault walk and no frontier computation: the smallest per-Prepare cost of any variant
- Backlinks are free and exact, so 'which referrers activate when I publish this' becomes a first-class answer
- Directly serves the operator-facing half of late binding: visibility into what a publication will change
- Obsidian already resolves aliases and headings, removing guesswork the exporter currently reimplements

**Novelty:** Relocates the authority for 'what links exist and who points here' from batch filesystem scanning to a live incrementally-maintained index, and converts the reverse-impact question from a computation into a UI affordance the operator acts on. It is the only variant where publishing a target immediately tells you, by name, which approved pages are about to change in the next release.

**Weakest link:** You end up building the graph twice and must keep the two in agreement forever. Fixtures, CI, the 22-page legacy rehearsal, and any exporter run outside Obsidian all need a non-plugin derivation path, so the plugin's graph is an accelerator with a mandatory shadow implementation — and every divergence between them is a class of bug that only appears in one of the two environments. Compounding it, the bridge contract is physically DUPLICATED: obsidian-plugin/bridge-client.js and an inlined copy inside obsidian-plugin/main.js (lines 15-252) both define it, with no shared test, so a contract change is a silent two-file drift hazard on the very seam this variant loads.

**Risks:**
- Two graph derivations that must agree; divergence is environment-specific and hard to test
- Bridge contract duplicated across bridge-client.js and main.js with no shared test
- metadataCache is Obsidian-version-coupled and undocumented in its staleness guarantees right after an edit
- Exporter validation of every descriptor is the real work anyway, so the plugin may buy less than it appears to
- Grows the trusted-input surface of a component whose current contract is deliberately minimal (four commands, path-validated)

### V5. V5 Shadow review root with the live site as the equivalence oracle

Change what counts as evidence rather than what the pipeline does. Make `init-semantic-site` able to initialize a SECOND, shadow review root against the same vault. Run the full semantic pipeline into the shadow root for all 22 legacy pages and for new notes, then diff the shadow public projection byte-for-byte against the currently-deployed site/src/content output. The only permitted differences are links whose targets have no approved snapshot (which must degrade to visible label). Promotion is a directory swap of two review roots — reversible, and the real workspace is never mutated until the diff is empty-or-explained. No hand-authored decisions.json, because the already-published output IS the decision oracle: whatever route a legacy link currently points at names the correct target.

**Strengths:**
- Removes hand-authored decisions.json by construction: the deployed routes are the decisions
- The real workspace and its 22 published pages are untouched until an explicit reversible promotion
- Turns acceptance criteria 3 and 4 into mechanical byte-diffs instead of judgement calls
- Composes with any identity strategy, so it can be built first and reused whichever of V1/V2/V3 wins
- Directly satisfies the problem's 'fixture-verified before touching the real review workspace' precondition

**Novelty:** The only variant that supplies an external, byte-level correctness oracle instead of asserting correctness from invariants. It reads the 22 legacy pages' problem backwards — the hard part is not parsing links out of the source, it is knowing which target each legacy link MEANT, and the deployed site already records that answer as a resolved route. It also makes the acceptance criteria mechanically checkable rather than reviewer-judged.

**Weakest link:** The oracle's route-to-identity mapping does not currently exist. ReferenceMigrationInventory.scanAstroRoutes requires `pageRef` AND `route` frontmatter in Astro content, and I verified that ZERO of the 40 published files under site/src/content carry either key — so the existing scan returns an empty map and the oracle is inert today. Rebuilding the mapping from the route CONVENTION (/<lang>/<collection>/<publicId>/, last segment matching the snapshot's frontmatter `id`) is feasible but is convention-inference, precisely the class of guessing constraint 2 forbids; one collection whose route segment does not match its review directory (already true: review/blog/* publishes under /ru/claims/*) turns a silent mis-mapping into a wrong-but-valid semantic bundle. The oracle must therefore fail closed on any route it cannot map exactly, and how many of the 19 distinct referenced routes survive that bar is unknown until measured.

**Risks:**
- Route-to-identity oracle must be built from convention because the declared metadata is absent — fail-closed behavior is essential and will likely block some pages
- Doubles review-root disk and needs a promotion/swap protocol that is itself lock-guarded
- Says nothing about how identity allocation works: must be composed with V1, V2, or V3, so it is not a complete answer alone
- The deployed site can drift from the approved snapshots, making the oracle stale and its verdicts untrustworthy without a freshness check

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** A shadow review root plus a byte-equivalence diff against deployed output is reusable infrastructure for every future change to release shape — schema v2, route restructuring, collection renames, translation-pipeline swaps — not just this migration. It converts 'we believe approved bytes are unchanged' (acceptance criterion 4) from a reviewed claim into a standing regression check, and it is the only variant that makes touching the real 22-page workspace a reversible directory swap rather than an in-place edit.
