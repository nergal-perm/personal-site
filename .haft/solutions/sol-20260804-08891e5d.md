# Solutions for: S03 — Prepare the first essay candidate

Problem: prob-20260804-97ecd928

## Variants (2)

### V1-configurable-command-strategy. Configurable TranslationCommand strategy, defaulting to exporter-java's exact Codex invocation

TranslationWorker is a minimal String-in/String-out port. Its real adapter, ProcessTranslationWorker, delegates argv construction to an injected TranslationCommand strategy (argsFor(workdir, prompt): List<String>) rather than building the command itself. The only implementation wired in S03, CodexTranslationCommand, replicates exporter-java's CodexRunner.defaultCommandForResolved exactly: `codex exec --ephemeral --sandbox workspace-write --skip-git-repo-check -C <workdir> --output-last-message <workdir>/agent-message.txt <prompt>`, no stdin, bounded timeout with forced termination on expiry (evidenced 1:1 from CodexRunner). The result carrier is also evidenced: the process is expected to write `candidate.en.md` into the workdir; ProcessTranslationWorker reads that file after the process exits and treats a missing file as failure.

**Strengths:**
- Operator's explicit instruction: reuse the exact evidenced Codex command for now, keep it swappable, not hard-coded into the Worker
- Zero new argv-templating machinery invented speculatively — the seam is just an injected interface with one concrete implementation
- Tests stay worker-neutral: the in-memory fake never touches TranslationCommand or ProcessBuilder at all

**Novelty:** Separates 'which external tool runs' (swappable via TranslationCommand) from 'how the exporter waits for and reads back a result' (fixed workdir-file convention), so gemini/agy can be wired in later purely by adding a new TranslationCommand implementation with no change to ProcessTranslationWorker or the port contract.

**Weakest link:** The result-file convention (candidate.en.md written into the workdir) is currently a convention enforced only by the prompt text handed to whichever CLI is configured — a misbehaving or differently-prompted tool that doesn't honor it will look identical to a translation failure, which is actually the correct fail-closed behavior but gives a generic diagnostic rather than a tool-specific one.

**Risks:**
- If a second real tool is wired later with a genuinely different result-carrying convention (e.g. stdout instead of a file), the fixed workdir-file convention would need to become configurable too — deferred until that's a real, not speculative, need

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** TranslationCommand is the exact seam a future --translator CLI flag or config-driven tool selection would plug into, without touching ProcessTranslationWorker's process-management logic.

### V2-hardcoded-codex. Hard-code the Codex invocation directly inside ProcessTranslationWorker

Build the codex argv list inline inside ProcessTranslationWorker with no separate strategy interface.

**Novelty:** Simpler for exactly one tool, at the cost of requiring a rewrite of ProcessTranslationWorker itself (not just a new implementation) to add gemini/agy later.

**Weakest link:** Directly contradicts the operator's explicit instruction that the command must be configurable, not hard-coded into the Worker itself.

**Risks:**
- Violates an explicit operator requirement stated during this design pass
