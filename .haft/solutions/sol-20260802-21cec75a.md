# Solutions for: Wire up the real semantic link resolver end-to-end

Problem: prob-20260802-1803dd18

## Variants (8)

### V1. Registry-first lazy allocation inside Prepare

Original portfolio V1. Initialize an empty semantic workspace, then have each Prepare lazily reconcile only its current authored targets into the numeric VaultReferenceCatalog before installing the candidate triple.

**Strengths:**
- No separate operator action
- Reuses the existing semantic map and materializer
- Small catalog

**Novelty:** Minimum-new-concepts baseline: identity allocation remains a side effect of preparing one page.

**Weakest link:** Prepare currently holds only a shared semantic lease; making it write the catalog admits lost updates and duplicate allocations under concurrent Prepare, while unresolved not-yet-catalogued targets can be silently dropped.

**Risks:**
- Violates the hard concurrency constraint unless all Prepare invocations are serialized
- Recovery after allocation followed by candidate failure is undefined
- First references to unseen targets can be lost

**Diversity role:** Original portfolio; baseline registry allocation

### V2. Path-or-ID-derived identity with rename index

Original portfolio V2. Derive targetRef from frontmatter id when present, otherwise from normalized vault path; demote the catalog to a rename/alias index and let Prepare derive unseen target identities without writing allocation state.

**Strengths:**
- No allocation race
- Unseen private targets resolve immediately
- Catalog loss is less damaging

**Novelty:** Deletes allocation by making identity a pure function of source data.

**Weakest link:** For id-less notes, a rename changes identity silently; preserving it requires reintroducing durable rename state or mandating IDs, neither of which this original option enforces.

**Risks:**
- Silent link decay after id-less rename
- Two targetRef formats must be reconciled
- Path fallback violates rename-stability

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** The derivation function points toward a rebuildable identity model, even though path fallback disqualifies it as the final standalone solution.

**Diversity role:** Original portfolio; derived identity

### V3. Separate publication-frontier reconciliation operation

Original portfolio V3. Add an idempotent reconcile-semantic-targets command that takes an exclusive lease, allocates identities for the one-hop publication frontier, and leaves Prepare a read-only catalog consumer that blocks on missing identities.

**Strengths:**
- Writers are exclusive and readers shared
- Idempotent recovery
- Missing targets block loudly

**Novelty:** Separates registry writing from page preparation so each operation has the correct lock mode.

**Weakest link:** It creates a second operator-visible link-maintenance action; auto-chaining it would blur the separation and reintroduce lock/transaction coupling.

**Risks:**
- Contradicts the no-separate-link-maintenance acceptance criterion
- Duplicates frontier/link parsing
- Automatic exclusivity can surprise the operator

**Diversity role:** Original portfolio; explicit maintenance transaction

### V4. Obsidian-owned link graph with exporter validation

Original portfolio V4. Have the Obsidian plugin send resolved targets and backlinks through an expanded bridge contract; the exporter revalidates source bytes and descriptors while using the plugin graph for operator visibility and closure.

**Strengths:**
- Fast bounded Prepare graph lookup
- Backlink impact is visible to the operator
- Aliases and headings use Obsidian resolution

**Novelty:** Moves graph derivation and reverse-impact visibility to Obsidian's live metadata index.

**Weakest link:** Non-Obsidian fixtures, CI, and CLI runs still require an independent derivation path, so two graph implementations and duplicated bridge contracts must stay consistent; it also does not itself settle durable identity or migration.

**Risks:**
- Environment-specific graph divergence
- Duplicated main.js/bridge-client.js contract
- Incomplete standalone identity and legacy-upgrade strategy

**Diversity role:** Original portfolio; graph authority and UI accelerator

### V5. Shadow review root with deployed-site equivalence oracle

Original portfolio V5. Run the semantic pipeline in a second review root, compare its public projection byte-for-byte with deployed output, and promote through a reversible root swap only when differences are empty or explained.

**Strengths:**
- Protects the real review workspace
- Makes legacy output preservation mechanically testable
- Reusable regression harness

**Novelty:** Changes the evidence model by adding a reversible shadow workspace and external byte-level oracle.

**Weakest link:** The live Astro output lacks the pageRef/route metadata needed for exact route-to-identity recovery, and the option does not specify identity allocation; convention-based recovery would guess where the constraints require blocking.

**Risks:**
- Current oracle is inert without exact route metadata
- Needs its own lock-guarded promotion protocol
- Incomplete standalone identity strategy

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** A shadow-root equivalence check remains valuable migration infrastructure whichever identity strategy is later chosen.

**Diversity role:** Original portfolio; verification harness

### V6. Receipt-pinned transactional Prepare

Refined portfolio V1. Under the long shared semantic lease, use a short catalog-writer transaction with monotone ensure, immutable revisions and HEAD compare-and-swap; return a page-scoped binding receipt and revalidate only those bindings before candidate install and approval.

**Strengths:**
- Concurrent translations can overlap
- Unrelated allocations do not stale candidates
- Failed translation leaves only legal unused identity

**Novelty:** Hardens lazy allocation into a revisioned, receipt-pinned internal transaction without a separate operator command.

**Weakest link:** Monotone evidence cannot distinguish deletion from rename for id-less notes, so stale paths and aliases accumulate and eventually require explicit identity repair.

**Risks:**
- Requires a new ensure API and immutable revision store
- Page-scoped planning is prerequisite
- Durability and compaction need fault injection

**Diversity role:** Refined portfolio; transaction and concurrency protocol

**Rollback:** Introduce behind a fixture-only schema marker before any real-workspace activation.

### V7. Publication-frontier Zettelkasten identity

Refined portfolio V2. Use the vault source id as durable semantic identity and publicId only as route slug. Require a stable unique immutable ID on the prepared page and every uniquely resolved direct private target before Prepare may proceed; forbid path fallback and make the catalog a rebuildable index.

**Strengths:**
- No central allocation race
- Identity survives ordinary renames
- Catalog can be rebuilt from source notes
- Uses the existing stableNoteId/publicId separation

**Novelty:** Hardens derived identity by deleting path fallback and making source-ID admission an explicit publication-frontier invariant.

**Weakest link:** The gate must enforce uniqueness, immutability and complete direct-target coverage; copied or changed IDs must fail closed, and missing IDs require human assignment before rerunning Prepare.

**Risks:**
- Duplicate copied IDs must hard-block
- ID change after approval is identity loss
- Private IDs must never leak into public output

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Frontier IDs also make registry allocation or approval-time linking safer if source IDs are not ultimately exposed as targetRef.

**Diversity role:** Refined portfolio; source-owned identity and admission invariant

**Rollback:** Begin as a read-only frontier audit and fixture validation gate; do not rewrite source notes or approved snapshots automatically.

### V8. Relocatable candidates with approval-time linker

Refined portfolio V3. Prepare RU/EN plus a symbolic-reference sidecar without allocating targetRef; mark-reviewed presents a hash-bound binding certificate, then under an exclusive semantic lock revalidates, allocates or reuses IDs, binds the PageReferenceMap, and commits the approved triple atomically.

**Strengths:**
- Prepare remains allocation-free
- Semantic destination is explicitly reviewed
- Ambiguity and drift fail closed

**Novelty:** Moves identity binding to an auditable compiler-linker boundary at explicit approval.

**Weakest link:** An id-less target lacks durable pre-allocation identity: path-plus-file-hash certificates stale on benign rename/edit, while relaxing them risks binding a replacement note.

**Risks:**
- Needs new symbolic codec and preview/confirm CAS
- Approval becomes serialized
- Partial catalog/page commit needs idempotent recovery

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** A relocatable candidate format can support offline/CI preparation and alternative identity stores.

**Diversity role:** Refined portfolio; compiler-linker and approval boundary

**Rollback:** Pilot only in fixture workspaces behind a new schema version; retain v1 approved triple readability.
