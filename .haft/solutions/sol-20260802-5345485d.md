# Solutions for: Wire up the real semantic link resolver end-to-end

Problem: prob-20260802-1803dd18

## Variants (3)

### V1. Receipt-pinned transactional Prepare

Keep Prepare as one operator action, but split identity allocation into short internal subtransactions beneath the existing long shared semantic lease. A separate catalog-writer lock performs a monotone ensure of the current page and its exact target footprint, publishes an immutable catalog revision through HEAD compare-and-swap, and returns a binding receipt; translation runs against that receipt, then candidate installation and mark-reviewed both revalidate only those bindings. This requires extracting page-scoped semantic planning because the current resolveEntry builds plans for every selected publication; initialization seeds an empty revision and legacy pages use the same path.

**Strengths:**
- Concurrent slow translations can overlap without lost allocations or whole-Prepare exclusive locking.
- Unrelated later allocations do not invalidate a candidate receipt.
- Failed translation leaves only a legal never-reused identity, never changed approved bytes.
- Existing atomic candidate and published triple boundaries remain intact.

**Novelty:** A substantial hardening of registry-first allocation: not merely a mutex around V1, it replaces partial full-snapshot reconcile with monotone ensure, immutable revisions, selective optimistic validation, and a second check at approval. Unlike V3, exclusivity is a short internal phase with no operator-visible maintenance command.

**Weakest link:** Bounded monotone evidence can prove that a note exists but cannot prove that an omitted id-less catalog entry was deleted rather than renamed. Stale paths and aliases therefore accumulate and may eventually force an explicit identity repair; weak alias/title matching cannot safely paper over that gap.

**Risks:**
- The current reconcile method tombstones every omitted entry, so a distinct ensure API and storage protocol are mandatory.
- Page-scoped planning is a prerequisite; otherwise each Prepare still needs identities for every selected note.
- Catalog revision durability and compaction need fault-injection across supported filesystems.
- A later identity collision makes approval stale and forces re-Prepare.

**Diversity role:** transaction and concurrency protocol

**Rollback:** The new revision store can be introduced behind a schema marker; before real-workspace activation, reverting to the previous catalog format is fixture-local and does not touch approved snapshots.

### V2. Publication-frontier Zettelkasten identity

Use the vault's existing source id as the durable semantic subject identity and keep publicId solely as the route-facing publication slug. Make id mandatory, immutable, and unique before a note enters the semantic publication frontier: that frontier includes each prepared page and every uniquely resolved private target whose link must activate later, not merely notes after publish:true is set. targetRef becomes a namespaced representation of id, path fallback is forbidden, and the central catalog becomes a rebuildable path/title/alias index; the live vault already has ids on 32 of 34 publish:true notes, including 22 twelve-digit Zettelkasten-style ids.

**Strengths:**
- No central allocation race and no rename index is needed for identified notes.
- Catalog loss becomes recoverable from source notes and approved reference maps.
- The proposal reuses a field the exporter already reads as stableNoteId while publicId remains a separate route slug.
- Human-readable IDs improve review and migration diagnostics compared with opaque allocated numbers.

**Novelty:** A deliberate hardening of old V2 rather than a disguised duplicate: V2 silently falls back to path-derived identity for id-less notes, while this variant deletes that unsafe fallback and turns the already-existing id/publicId separation into an explicit publication-admission invariant. Identity travels with the subject and survives ordinary renames without a retained allocation ledger.

**Weakest link:** The admission frontier must be enforced before referrer approval. Requiring IDs only on publish:true notes is too late; if a private target lacks an ID, Prepare must either block and impose an authoring-hygiene step or fall back to a symbolic linker, so the promise of effortless first-reference late binding depends on upstream ID discipline.

**Risks:**
- Existing duplicate or copied IDs must hard-block when either note enters the semantic frontier.
- Missing IDs turn Prepare into a validation stop unless note-creation tooling assigns them beforehand.
- Changing or stripping an ID after approval must be treated as identity loss, never reconstructed from path.
- The private identity must be excluded from public metadata and covered by the vault-ref leak checks.

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** Even if source id is not adopted directly as targetRef, enforcing unique immutable IDs on the semantic frontier removes rename ambiguity and makes both transactional catalog allocation and approval-time linking safer. It opens a rebuildable, multi-machine identity model without committing yet to catalog deletion.

**Diversity role:** identity ownership and authoring invariant

**Rollback:** Start with a read-only frontier audit and validation gate. No source rewrite or approved-snapshot change is needed until the operator explicitly adopts the ID policy.

### V3. Relocatable candidates with an approval-time linker

Make Prepare a read-only compiler with respect to identity allocation: it installs RU/EN plus a relocatable symbolic-reference sidecar, blocking ambiguous symbols but not allocating targetRef values. Mark-reviewed exposes a hash-bound binding certificate over the exact reviewed bytes and target evidence; on explicit confirmation it takes the exclusive semantic lock, revalidates the certificate, allocates or reuses IDs, produces a fully bound PageReferenceMap, and atomically commits the published triple. Legacy pages follow the same object-to-linked approval path, and later target publication still changes only release projection.

**Strengths:**
- Prepare stays allocation-free and compatible with shared-reader locking.
- The semantic destination—not merely opaque targetRef bytes—is explicitly reviewed.
- Ambiguity and preview drift fail closed before approved bytes move.
- Final RU/EN hashes, occurrence order, and bound references are validated and committed together.

**Novelty:** Moves both the semantic transaction boundary and the artifact model: Prepare emits object code and approval performs auditable linking. Unlike V1, allocation cannot corrupt or stale a prepared candidate; unlike V3, there is no pre-Prepare maintenance action; unlike V5, the certificate is an internal proof of semantic binding rather than an external byte oracle.

**Weakest link:** An id-less target has no durable pre-allocation identity. A certificate based on normalized path plus target-file hash is honest but brittle under harmless edit or rename; relaxing it risks approving a replacement note, so the design either needs the frontier-ID invariant or accepts frequent stale/re-Prepare outcomes.

**Risks:**
- Requires a new relocatable-candidate codec and a preview/confirm CAS protocol.
- The final bound map differs from the prepared symbolic sidecar, so certificate provenance must be durable and review-visible.
- Exclusive approval serializes Prepare, build, and other approvals during the linking commit.
- Catalog-first success followed by page-commit failure leaves unused IDs and needs an explicit idempotent recovery contract.

**Stepping stone:** yes — opens future possibilities

**Stepping-stone basis:** A relocatable candidate format separates semantic authoring from identity authority, opening offline or CI preparation, alternative identity stores, and multi-workspace linking even if approval-time allocation itself proves too disruptive.

**Diversity role:** compiler-linker and approval-boundary restructure

**Rollback:** The relocatable format can be piloted only in fixture workspaces under a new schema version; existing v1 approved triples remain readable and untouched.
