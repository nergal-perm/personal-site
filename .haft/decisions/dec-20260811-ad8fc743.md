# write-publication-contract emits a standalone PublicationContract document sourced from EssayAdmission.fieldRules(), with a shared fixture table proving contract/runtime agreement

## 1. Problem Frame

**Signal:** EssayAdmission (publication-exporter/src/main/java/dev/eugene/publicationexporter/admission/EssayAdmission.java) hardcodes the only content kind's admission rules (publish=true, publicCollection="blog", publicContentType="essay", slug-shaped publicId, non-blank id/title/description) as Java conditionals with no externally readable description. Authoring tools (the Obsidian plugin, editors) have no deterministic, machine-readable statement of what fields are required, what values are allowed, and what a valid publication body looks like for the kinds this exporter edition currently implements. There is also no harness proving that a published contract and the exporter's own runtime validation logic (EssayAdmission today) agree — the two could silently drift.

**Constraints:**
- One command response plus one shared fixture table — no new production adapter
- Do not generate internal OOP design (class shapes) from the external contract; the contract is a projection of admission rules, not their source
- No whole-vault discovery in this slice
- No new content kind introduced in this slice
- In-memory/CLI acceptance subset stays well under the 1s slice budget

**Acceptance:** A new `write-publication-contract` command emits a deterministic, schema-described contract for every content kind implemented so far (currently blog/essay only). Requesting the contract twice for the same exporter edition with no contract changes yields byte-equivalent output after declared serialization normalization. A shared fixture table drives both runtime admission validation and a contract-conformance harness; any fixture the published contract accepts but runtime validation rejects (or the reverse) fails the exporter edition's acceptance suite. Discovering notes across the vault and adding any new content kind remain explicitly out of scope.

## 2. Decision

**Selected:** write-publication-contract emits a standalone PublicationContract document sourced from EssayAdmission.fieldRules(), with a shared fixture table proving contract/runtime agreement

**Selection policy:** Resolve the functional shape via collaborative-design first (contract response shape, standalone-vs-BridgeResponse fork), settle the technical shape via a second collaborative-design pass constrained to zero new adapters/ports (pure in-process slice), then implement task-by-task with independent spec/quality/SBPP/OO-design review after each task and one whole-branch review at the end; any Important/Critical finding either gets fixed or is explicitly parked with a documented ruling the final review re-triages, never silently dropped.

**Why selected:** A standalone PublicationContract document (contractVersion + kinds[]) keeps a semantically unrelated response shape (a declarative document, not an operation outcome) out of BridgeResponse, which prob-20260808-08cf74cd already flags as an overgrown 15-parameter multi-shape DTO — adding a 16th case would have compounded that debt instead of avoiding it. EssayAdmission gains a FieldRule/fieldRules() seam that admit() does not itself consume, so the contract reads real declared rule data without EssayAdmission being restructured to fit the external contract's shape. A fixture table shared between EssayAdmissionTest and a new PublicationContractConformanceTest gives ADM-06's 'validator and published contract disagree' scenario a real, catchable failure mode: three independent readings of each fixture (its own label, the contract's independent interpretation, EssayAdmission's real verdict) must agree.


**Invariants:**
- The contract is never wrapped in BridgeResponse or exposed through bridge-contract/schema-v2.json's conformance surface.
- EssayAdmission.admit(...) and its existing private require* methods' behavior are never changed by contract-reading code.
- Every field FIELD_RULES/EssayPublicationContract describes must be re-provable against EssayAdmission's real admit() verdict via the shared fixture table — no fixture-table drift between EssayAdmissionTest and PublicationContractConformanceTest.

**Spec sections:**
- ADM-06

**Post-conditions:**
- [ ] `write-publication-contract` returns exit code 0 and a PublicationContract JSON document on every invocation.
- [ ] Two consecutive invocations produce byte-identical stdout.
- [ ] The essay kind's 7 required fields (publish, publicCollection, publicContentType, publicId, id, title, description) are present with correct type/allowedValues/pattern/nonBlank.
- [ ] WritePublicationContractCommand and the three contract DTOs (plus FieldContract$Type) are registered in reflect-config.json for the GraalVM native build.

## 3. Rationale

**Counterargument:** The strongest case against this shape is the one the applying-sbpp reviewer raised: FIELD_RULES and admit()'s hand-written require* methods encode the same six rules twice as data and as code, with no structural mechanism forcing them to stay in sync — only the fixture-table conformance test catches drift, and only for fixtures someone remembered to add. A more tightly coupled design (admit() itself iterating FIELD_RULES) would make drift structurally impossible, at the cost of restructuring already-working, already-reviewed validation logic to serve an external contract's shape.

**Selected variant weakest link:** FIELD_RULES (contract data) and EssayAdmission.admit()'s hand-written require* methods (runtime validation) encode the same six rules twice, with no structural sharing of the validation algorithm itself. If a seventh rule is ever added to admit() without a matching FieldRule, the contract silently ships incomplete unless PublicationContractConformanceTest's fixture table is extended to exercise that new condition.

## 4. Consequences

**Rollback plan:**
Triggers:
- A future kind (S17a-f) reveals FieldRule's flat-data shape cannot express that kind's admission rules without contortion.
- The parked applying-sbpp switch-dispatch finding is revisited and a real multi-call-site type-switch problem materializes once more than one place switches on FieldRule.Kind.
Steps:
1. Revert the four S15 commits (f1154bd, 7f59b26, bd59db4, bf93a1d) plus the reflect-config fix (00fde10).
2. No data migration needed — the command is stateless and read-only; no persisted artifact depends on the contract's shape.
Blast radius: publication-exporter's admission and contract packages, one CLI command, one native-image config file. No effect on prepare/approve/release/site paths or any other command.
