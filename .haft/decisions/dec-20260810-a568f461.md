# S12: MarkdownNormalizer scanner (fenced/inline code protection + Obsidian comment stripping) wired into PrepareHandler, normalize-once-and-reuse

## 1. Problem Frame

**Signal:** publication-exporter's prepare pipeline (PrepareHandler) installs the Russian candidate body verbatim from the admitted source, with no Markdown normalization step. PCM-04 (openspec/specs/public-content-model/spec.md) requires that Obsidian-only comment syntax (%%...%%) be removed from publishable prose while code, inline code, and other declared protected regions are left semantically unchanged — including any link-like, wiki-link, or embed-like text that happens to sit inside those protected regions, which must survive byte-for-byte. Neither requirement is implemented yet: PCM-04 is unimplemented in the new exporter (S01-S11 never touched Markdown content, only frontmatter/identity/workflow). The legacy exporter-java's MarkdownScanner class and MarkdownNormalizationTest are evidence/oracle only per this project's standing rule (CLAUDE.md, implementation-plan.md preamble) — not a design template or code donor for publication-exporter.

**Constraints:**
- Governed by openspec/implementation-plan.md's slice discipline: one failing system-boundary acceptance test in, one visible result out, at most 1-3 new OpenSpec scenarios, at most one new production boundary adapter (S12 needs none — pure in-process transform), in-memory acceptance subset under 1 second
- Explicitly excludes resolving actual links, transclusions, and assets (S13/S14's scope)
- exporter-java's MarkdownScanner/MarkdownNormalizationTest are evidence/oracle only, not a code donor — no direct port of its class or package structure into publication-exporter
- Governed by /nullables, /applying-sbpp, /elegant-objects, /oo-design-guide per this project's standing convention for exporter code
- The acceptance boundary is one fixture through prepare; narrow unit tests only if the scanner has genuinely combinatorial protected-region cases

**Acceptance:** Preparing an essay whose Russian source contains an Obsidian comment produces a candidate with that comment absent from public content; preparing an essay whose source contains link-like, wiki-link, or embed-like text inside a fenced code block or inline code span produces a candidate where that protected text is byte-for-byte unchanged. Both scenarios pass through the real `prepare` CLI/handler path (PCM-04's two baselined scenarios in openspec/specs/public-content-model/spec.md), and the full acceptance suite (currently 484 publication-exporter tests) stays green.

## 2. Decision

**Selected:** S12: MarkdownNormalizer scanner (fenced/inline code protection + Obsidian comment stripping) wired into PrepareHandler, normalize-once-and-reuse

**Selection policy:** Minimal-scope implementation matching PCM-04's literal wording (fenced code + inline code as the only protected-region kinds; no HTML comments, no raw HTML pre, no link/transclusion/asset handling — deferred to S13/S14), following the plan's slice discipline (zero new production adapters, one new in-process transform). Selected via two collaborative-design passes (functional requirements, then technical design) with the operator before any code was written.

**Why selected:** A leftmost-match-among-candidates scanner (fenced-code span, inline-code span, next %% occurrence; copy-through; repeat) correctly resolves which construct wins when one could contain text matching another — the natural, correct shape for this class of problem, independently arrived at and cross-checked against exporter-java's MarkdownScanner test suite as validation evidence only (never as a code donor). MarkdownNormalizationOutcome (sealed interface + resolve(onNormalized, onUnclosedComment)) mirrors this codebase's existing TranslationOutcome pattern for explicit business-outcome modeling. An unclosed Obsidian comment blocks preparation with a diagnostic rather than silently extending to end-of-body and stripping the rest of the article (exporter-java's legacy behavior) — a deliberate fail-closed divergence consistent with this project's dominant convention (ambiguous asset lookup, malformed identity, etc. all block rather than guess). Normalization runs once, immediately after NoteIntake admission, and the same normalized text is reused for the approved-baseline-unchanged check (RussianDiff), the translation job, and the installed candidate body — required so a comment-only edit correctly counts as unchanged for the existing skip-optimization, and so the freshness re-check (sourceStillMatches/sourceFreshness) doesn't falsely report stale or falsely swallow a workflow-status write.


**Invariants:**
- The approved-unchanged short-circuit, the translation job, and the installed candidate body all see the exact same normalized text within one prepare() call.
- A closing or opening backtick run for inline code must be maximal (neither preceded nor followed by another backtick) to count as a valid delimiter, matching CommonMark's code-span rule exactly.
- An unclosed Obsidian comment never silently strips or truncates content; it always blocks with a diagnostic and mutates no candidate, approved snapshot, or workflow state.
- A plain essay with no comments and no protected regions remains byte-identical after normalization (dec-20260804-9f43c17f's pass-through guarantee, unaffected).

## 3. Rationale

**Counterargument:** A reviewer could argue the scope is too narrow — HTML comments and raw HTML <pre> blocks are real Markdown constructs exporter-java already protects, and deferring them means this slice's protected-region model is incomplete relative to what real vault content might eventually need. Accepted as correct for now: PCM-04's baseline text only names "code, inline code, and other declared protected regions," and the plan's slice discipline explicitly warns against speculative breadth: the scanner's architecture (leftmost-match among candidate generators) extends cleanly with one more candidate generator whenever a real requirement needs HTML comments or raw <pre>, so nothing here forecloses that future slice.

**Selected variant weakest link:** The scanner's correctness rests entirely on two regexes (FENCE_OPEN/FENCE_CLOSE, INLINE_CODE) whose edge cases are genuinely easy to get subtly wrong — proven twice in this same slice: the closing-side maximal-run guard was missed in the first fix round and only caught by a parallel code-quality review, and the symmetric opening-side guard was missed even after that fix and only caught by the final whole-branch review at max effort. A third such asymmetry cannot be ruled out by inspection alone; any future change to these patterns should re-run the full existing regression suite (10 targeted tests covering both sides of both regexes) as a first-line defense, not just visual review.

- A future slice (S13 links, S14 assets) finds the leftmost-match scanner architecture cannot cleanly add a third candidate-region kind
- A real vault note surfaces a Markdown construct (HTML comment, raw <pre>) that needs protection sooner than S13/S14
Steps:
1. Revert the four S12 commits (922f7e3..c5992d3) as one range; no approved or release state depends on Markdown normalization yet since it only affects candidate-body content
