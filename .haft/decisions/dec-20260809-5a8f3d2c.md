# G5: macOS Apple-Silicon GraalVM native executable is the sole supported distribution

## 1. Problem Frame

**Signal:** The first real-plugin trial after S07 succeeded with the GraalVM native `publication-exporter` executable on macOS Apple Silicon, but no recorded distribution contract says which executable an operator should configure or which environments the project supports.

**Constraints:**
- macOS Apple Silicon is the only supported runtime for the foreseeable future.
- Windows and Linux are entirely outside scope: no compatibility promise, package, installer, CI target, or support commitment.
- The Obsidian plugin invokes an operator-configured absolute executable path; it does not build, download, update, or discover the exporter.
- GraalVM native execution is the supported publishing runtime; JVM/JAR execution may remain for development and diagnosis only.
- This decision does not add an updater, cross-platform packaging, code signing/notarization, or a publication-workflow feature.

**Acceptance:** One documented, supported macOS Apple-Silicon native-executable route is available to the plugin operator, while the project makes no claim of Windows, Linux, automatic installation, automatic updates, or deployment support.

## 2. Decision

**Selected:** V1-macos-arm64-native — macOS Apple-Silicon GraalVM native executable.

**Selection policy:** Choose the smallest distribution contract proven by the real-plugin pilot, with the fewest operator prerequisites and no unsupported-platform promise.

**Why selected:** The native executable already completed the live review-workspace and isolated-site pilot, and lets Obsidian launch the bridge without a Java runtime at the publishing point. An explicit configured path makes ownership legible: the operator installs/chooses the binary; the plugin invokes it; neither component pretends to manage releases.

**Invariants:**
- Only a macOS Apple-Silicon native executable is a supported operator runtime.
- The plugin receives an absolute executable path from its settings and does not manage that executable's lifecycle.
- Windows and Linux are not supported targets and must not acquire accidental compatibility or release promises.
- JVM/JAR execution is never documented as a second supported end-user distribution route.

**Admissibility:**
- NOT: No automatic binary discovery, installation, updating, signing/notarization, or cross-compilation work.
- NOT: No change to bridge schema, approval semantics, release semantics, or site deployment.

## 3. Rationale

**Counterargument:** A JVM launcher could be easier to debug, and a universal distribution could prevent a later packaging redesign. Neither benefit outweighs adding runtime or multi-platform support obligations that the single-operator pilot neither needs nor proves.

**Selected variant weakest link:** The choice is intentionally narrow. A future Intel-Mac operator, macOS security-distribution requirement, or desire for managed installation would require revisiting G5 rather than silently treating the developer-built binary as a product installer.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| V1 macOS Apple-Silicon GraalVM native executable | **Selected** | Demonstrated by the real-plugin pilot; avoids a Java runtime in the operator path. |
| V2 macOS JVM/JAR launcher | Rejected | Adds Java runtime/version management to the publishing operator and is not the selected support boundary. |
| V3 multi-platform native releases | Rejected | Windows and Linux are explicitly excluded; supporting them now would be speculative packaging complexity. |

**Evidence requirements:**
- The native pilot evidence remains recorded in `note-20260809-c73f5b8a`.
- The build must continue to produce a macOS Apple-Silicon executable that answers the plugin's schema-v2 commands.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| A macOS Apple-Silicon operator can use the configured native executable for the first publication path without a JVM at invocation time. | Native `inspect-publication`, `build-from-review`, and `install-to-site` pilot plus Astro build. | All commands succeed for the pilot identity and Astro content validation passes. |
| The distribution boundary does not create unsupported platform obligations. | Distribution/operator documentation and release instructions. | No Windows or Linux installation, support, or CI target is introduced. |

## 4. Consequences

**Rollback plan:**
Triggers:
- An actual operator needs an Intel-Mac binary, Windows, Linux, signed/notarized distribution, or managed installation.
- The native executable cannot reliably satisfy the plugin contract after a supported build.
Steps:
1. Reopen G5 with the observed operator need and native failure evidence.
2. Select and record a replacement distribution contract before advertising or implementing the new target.
3. Keep the existing plugin configurable-path interface while the replacement is evaluated.
Blast radius: build/distribution documentation and the plugin executable-path instructions; no approved snapshot, review, release, or site content needs migration.

**Refresh triggers:**
- A second operator or a non-Apple-Silicon Mac becomes a real requirement.
- macOS signing/notarization or managed updates become necessary for the intended use.
- The translation worker or deployment model changes the single-operator trust assumption recorded for S08.

**Affected files:** `publication-exporter/pom.xml`, `publication-exporter/src/main/resources/META-INF/native-image/reflect-config.json`, `obsidian-plugin/main.js`, `obsidian-plugin/DEPLOY.md`
