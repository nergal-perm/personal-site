# Slice-by-slice outside-in sequence, S01 first, governed by paired Haft decisions and OpenSpec deltas

## 1. Problem Frame

**Signal:** The requirements baseline is complete, but implementing capabilities one by one would create large horizontal batches and long periods with no usable exporter behavior. The implementation needs a dependency-aware sequence in which every small increment produces a visible CLI, plugin, review-workspace, or site-output result.

**Constraints:**
- Each implementation slice begins with a failing system-boundary acceptance test and ends with observable exporter behavior.
- Keep the daily acceptance loop in-process and sub-second using in-memory adapters; add real I/O only behind behavior-proven contracts.
- Do not reproduce exporter-java classes or package structure.
- Start with one simple publication kind and one note; defer additional kinds, links, assets, queue refresh, migration, and native packaging until their own slices.
- Never weaken approval authority, path safety, candidate versus approved separation, or fail-closed bridge schema v2 behavior.
- Each slice names included OpenSpec scenarios and explicit exclusions; no foundation-only or refactoring-only slices.
- The plan is high-level and technology-neutral until the residual language, project-folder, bridge-carrier, translation-protocol, cutover, and distribution decisions are recorded.

**Acceptance:** A committed plan maps every one of the 47 requirements to a dependency-ordered implementation slice or an explicit conditional/deferred gate; every slice has one visible result, a minimal acceptance boundary, exclusions, and an outside-in test approach; the first path restores one real publication kind end-to-end before breadth is added.

## 2. Decision

**Selected:** Slice-by-slice outside-in sequence, S01 first, governed by paired Haft decisions and OpenSpec deltas

**Selection policy:** Adopt the plan as authored, without generating or scoring competing portfolios, because it was derived directly from the 47 baseline requirements against the slice-validity conditions in the plan itself (one failing acceptance test in, one visible result out, ≤3 scenarios, ≤1 adapter, sub-1s suite, no foundation-only milestone) and no rival sequencing was proposed to compare it against. Acceptance criterion: the plan's own seven slice-validity conditions plus full requirement-coverage-matrix traceability, checked directly rather than scored across variants.

**Why selected:** openspec/implementation-plan.md already applies vertical-slice discipline (one failing acceptance test in, one coherent visible result out, ≤3 new scenarios, ≤1 new adapter, sub-1s in-memory suite, no foundation-only milestone). Adopting it as-is keeps blast radius minimal and reversible per slice, isolates cross-cutting technology/schema choices into named gates (G1-G7) instead of letting them leak into slice code, and gives full requirement traceability via the coverage matrix. No further solution exploration is needed before acting on it.


**Invariants:**
- Every slice ends as one independently reviewable commit with the whole prior acceptance suite green.
- No slice quietly decides a G1-G7 gate through incidental code.
- Bridge schema major version 2 is the plugin-compatibility floor from S01 onward.

**Pre-conditions:**
- [ ] G1 (project identity) and G2 (bridge carrier) are decided before S01 implementation begins.
- [ ] An OpenSpec change is drafted for a slice's requirement delta before its acceptance test is written.

**Post-conditions:**
- [ ] S01 delivers `inspect-publication --json` blocked response accepted by the plugin's schema-v2 contract harness, covering BRG-01/02/03.
- [ ] Milestone A (S01-S07) proves one plain blog/essay end-to-end before any breadth work starts.

**Admissibility:**
- NOT: No production code outside the new <new-exporter> sibling directory and the shared bridge contract carrier.
- NOT: No slice implemented without a preceding OpenSpec change and a red acceptance test.

## 3. Rationale

**Counterargument:** Drafting every slice's OpenSpec delta upfront would reduce mid-stream churn, but it front-loads speculative detail the plan's own stopping rules argue against; slice-by-slice authoring keeps each decision evidence-based and reversible.

**Selected variant weakest link:** Gates G1-G7 sit outside the slice sequence; if any gate is decided implicitly inside a slice's code instead of as its own recorded decision, that slice bakes in an undocumented architecture choice the plan explicitly forbids.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Slice-by-slice outside-in sequence, S01 first, governed by paired Haft decisions and OpenSpec deltas | **Selected** | openspec/implementation-plan.md already applies vertical-... |
| Layer-first: build all ports/adapters before any behaviour | Rejected | Contradicts the plan's outside-in discipline and its explicit ban on foundation-only or abstraction-only milestones. |
| Front-load all 23 slices' OpenSpec deltas before writing any code | Rejected | Front-loads speculative detail; the plan's own stopping rules require splitting/reassessing per slice based on evidence, which upfront authoring can't reflect. |

**Evidence requirements:**
- The acceptance suite stays green after every slice commit.
- The plugin contract harness accepts every schema-v2 response newly emitted by a slice.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| S01's in-memory acceptance subset stays under 1 second | wall-clock time of the S01 acceptance test run | < 1s |
| S01 introduces exactly one new production boundary adapter | count of new production adapters merged in the S01 commit | == 1 |

## 4. Consequences

**Rollback plan:**
Triggers:
- A slice cannot stay under its 1s/adapter/scenario budget without a written reason and split
- The plugin's schema-v2 harness rejects a response a slice claims to satisfy
Steps:
1. Revert the offending slice's single commit
2. Re-open the slice-sequencing problem to re-split or re-scope the slice
Blast radius: One reviewable commit; no approved or release state exists yet for the new exporter, so nothing durable is at risk this early.

**Refresh triggers:**
- Any G1-G7 gate decision changes
- Bridge schema major version bumps beyond 2
- The plugin's contract harness shape changes

**Affected files:** openspec/implementation-plan.md
