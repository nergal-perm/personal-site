# LinkResolver + PublicNoteIndex, sharing an extracted ProtectedRegionScanner, wired into PrepareHandler's prepare/sourceFreshness paths

## 1. Problem Frame

**Signal:** Preparing an essay currently ignores link-like syntax entirely — S12 only strips Obsidian comments while protecting link-like syntax inside code regions. There is no resolution of internal wikilinks/transclusions against vault topology, so a public link, a private/unresolved link, and a private transclusion are all emitted unchanged (or worse, could leak absolute vault paths) into the candidate.

**Constraints:**
- Requirement PCM-03 only; do not implement stable semantic occurrence IDs (SEM-02) or late-bound target activation (SEM-04/05) — those are S19/S20
- Link resolution stays in-process (no new production adapter) until real vault lookup behaviour has emerged, per implementation-plan.md S13 acceptance boundary
- Must not leak vault topology (absolute paths, internal note IDs) through blocked/private link labels
- One to three new OpenSpec scenarios per slice discipline
- In-memory acceptance subset must stay under 1 second
- Whole prior acceptance suite must remain green

**Acceptance:** A three-note in-memory vault acceptance test shows: (1) one unambiguous link to a publicly-admitted note is converted to its public route, (2) one link to a private or unresolvable target renders as a safe plain-text label with no leaked path/route, (3) one private transclusion is blocked before candidate replacement rather than being inlined or silently dropped. PCM-03 requirement is satisfied. Full suite stays green; no new production adapter beyond in-process resolution (real vault lookup deferred per plan).

## 2. Decision

**Selected:** LinkResolver + PublicNoteIndex, sharing an extracted ProtectedRegionScanner, wired into PrepareHandler's prepare/sourceFreshness paths

**Selection policy:** Minimal-slice discipline from openspec/implementation-plan.md: zero new production adapters, reuse existing ports and established codebase patterns (sealed outcome types, normalize-once-and-reuse) over inventing new machinery, and defer anything overlapping a later slice's already-planned scope (S16 discovery, S19/S20 semantic references) rather than building it speculatively now.

**Why selected:** Reuses the already-shipped VaultReader port (listPublishCandidates + NoteIntake.admit) to build a per-call known-public-notes index -- zero new production adapters, matching the plan's slice discipline. Extracts ProtectedRegionScanner out of MarkdownNormalizer (S12) into a shared primitive, exactly the extension point S12's own design.md anticipated, so link-like text inside fenced/inline code stays provably untouched via one source of truth rather than a duplicated regex. Routes are locale-neutral (/essays/{publicId}/, no /ru//en/ segment) because resolution runs once on the RU body ahead of translation and the same text is reused untranslated in the EN candidate -- this is what keeps EnglishCandidateValidator's existing internal-route leak check from ever tripping on a route this feature itself produced. Ambiguous targets fold into the same safe-label treatment as private/unresolved ones (no dedicated diagnostic), matching PCM-03's baseline wording and the operator's explicit call that disambiguation is the author's responsibility.


**Invariants:**
- A private, unresolved, or ambiguous link's output never contains a vault path, private route, source identifier, or raw Obsidian link token
- Link-like text inside a fenced code block or inline code span is never resolved or altered by link resolution
- An asset-extension embed target is never treated as a note transclusion
- A blocked transclusion installs or replaces no candidate

**Post-conditions:**
- [ ] PCM-03's four scenarios (public-unambiguous, private/unresolved/ambiguous-linked, private-transcluded, asset-embed-untouched) pass as acceptance tests
- [ ] The whole prior publication-exporter acceptance suite remains green
- [ ] No new production boundary adapter exists beyond the existing VaultReader port

## 3. Rationale

**Counterargument:** The strongest case against this design: PublicNoteIndex.from(vaultReader) re-enumerates and re-admits every publish-candidate note on every single prepare() call (once per call, since sourceFreshness reuses rather than rebuilds it) -- at real-vault scale this is a real, uncached cost that a proper indexed lookup (S16-era) would avoid, and the locale-neutral route format is a novel convention this slice invents without a consuming site-side implementation to validate it against yet.

**Selected variant weakest link:** The deferred stale-index race: if a linked note's publish state changes during the synchronous translation-worker call, the referrer's candidate can still install with a route/label resolved against the pre-translation snapshot. Bounded by one worker call's duration, not open-ended, but not eliminated.
