# Versioned JSON Schema file at `bridge-contract/schema-v2.json`, validated by both sides' conformance tests

## 1. Problem Frame

**Signal:** The current exporter-java emits BridgeResponse.SCHEMA_VERSION = 3 while obsidian-plugin's bridge-client.js and main.js both hard-reject anything but schemaVersion === 2 — a live, verified drift. BRG-03 requires the contract be defined once and consumed by both sides' conformance tests; nothing currently plays that role.

**Constraints:**
- Must be consumable by both a Java test suite (publication-exporter) and a JS test suite (obsidian-plugin) without duplicating field/enum definitions in each language.
- Must express command names, required fields, field types, enum values, and v2 compatibility rules (unknown optional fields ignorable) per BRG-01/02/03.
- Must be versioned so a future major bump is an explicit, reviewable change, not silent drift.

**Acceptance:** A recorded decision states the carrier format and repository location for the bridge schema v2 contract, and how exporter and plugin conformance tests each consume it.

## 2. Decision

**Selected:** Versioned JSON Schema file at `bridge-contract/schema-v2.json`, validated by both sides' conformance tests

**Selection policy:** Pick the representation that a Java test (via a JSON Schema validator library) and a JS test (via ajv) can both validate against without re-encoding the contract per language, and that directly targets the observed schemaVersion 3 vs 2 drift. Acceptance criterion: BRG-03's four requirements (single-sourced command names, required fields, field types, enum values, compatibility rules) are checkable by an automated test on each side.

**Why selected:** JSON Schema is a single, language-neutral carrier with mature validator libraries on both the JVM (e.g. networknt/json-schema-validator) and Node (ajv) sides, so command shapes, required fields, types, and enums are defined exactly once. Placing it in a new top-level `bridge-contract/` directory (sibling to exporter-java/obsidian-plugin/site/publication-exporter) keeps it visibly shared infrastructure rather than owned by either consumer. This directly closes the concrete, already-observed drift: exporter-java's BridgeResponse.SCHEMA_VERSION = 3 against bridge-client.js/main.js hard-rejecting anything but schemaVersion === 2.


**Invariants:**
- Exactly one file (`bridge-contract/schema-v2.json`) is the source of truth for command names, required fields, field types, and enum values.
- Both publication-exporter's and obsidian-plugin's test suites validate real command output against this same file, not a hand-copied duplicate.

**Pre-conditions:**
- [ ] G1 is decided so publication-exporter's directory/build exists to host the Java-side conformance test.

**Post-conditions:**
- [ ] `bridge-contract/schema-v2.json` exists and encodes at least the `inspect-publication` blocked-response shape needed for S01.
- [ ] A publication-exporter conformance test validates its own JSON output against this file.
- [ ] A parallel plugin-side conformance test (or an existing one extended) validates against the same file.

**Admissibility:**
- NOT: No command's required fields, types, or enums are hand-duplicated in exporter or plugin source — both read/validate against `bridge-contract/schema-v2.json`.

## 3. Rationale

**Counterargument:** Codegen (Java types → TypeScript types or similar) would give compile-time safety on both sides, but it's a heavier toolchain investment than a two-consumer contract currently justifies; JSON Schema validated at test time is the minimal thing that closes the observed drift.

**Selected variant weakest link:** A JSON Schema file is only as good as both sides actually running validation against it in CI; if either conformance test is skipped or stubbed, drift can silently reappear exactly as it already has once (v3 vs v2).

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Versioned JSON Schema file at `bridge-contract/schema-v2.json`, validated by both sides' conformance tests | **Selected** | JSON Schema is a single, language-neutral carrier with ma... |
| Hand-maintained prose contract doc (e.g. a markdown table) | Rejected | Not machine-checkable; BRG-03 requires conformance tests to fail automatically on drift, which prose cannot do. |
| Define the contract only in the Java side and have the plugin trust it | Rejected | BRG-03 requires the contract be consumed by BOTH exporter and plugin conformance tests, not owned by one side. |
| Generate the JS types/validation from Java source (or vice versa) via a codegen step | Rejected | Adds a build-time cross-language toolchain dependency for a two-consumer contract; a shared static JSON Schema file is simpler and equally single-sourced. |

**Evidence requirements:**
- Both conformance tests fail if schemaVersion, a required field, or an enum value is changed without updating the shared file.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| A single JSON Schema file can express BRG-01/02/03's command/field/enum rules without per-language duplication | Whether the S01 conformance tests (Java + JS) both pass using only `bridge-contract/schema-v2.json` as the field/enum source | both pass, zero duplicated field lists |

## 4. Consequences

**Rollback plan:**
Triggers:
- JSON Schema proves too weak to express a compatibility rule BRG-03 needs (e.g. conditional required fields per command)
Steps:
1. Replace schema-v2.json's format (e.g. add a thin custom validator layer) while keeping the single-file-at-this-path convention
2. Re-open this gate decision
Blast radius: Contract carrier only; no approved/release state depends on its internal format yet.

**Refresh triggers:**
- A bridge command needs a compatibility rule JSON Schema can't express
- The schema major version bumps beyond 2

**Affected files:** obsidian-plugin/bridge-client.js, obsidian-plugin/main.js
