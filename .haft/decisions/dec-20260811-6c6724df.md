# PublicationKind/PublicationKinds seam extracted from EssayAdmission; NotePublicationKind added; blog/note proven through admit→prepare→approve→release

## 1. Problem Frame

**Signal:** The publication-exporter's admission and contract code is hardcoded to one kind. EssayAdmission (publication-exporter/src/main/java/dev/eugene/publicationexporter/admission/EssayAdmission.java) fixes REQUIRED_COLLECTION="blog"/REQUIRED_CONTENT_TYPE="essay" as class constants; NoteIntake.admit() (intake/NoteIntake.java) directly instantiates `new EssayAdmission()` with no kind-selection seam; EssayPublicationContract.kind() is a static single-kind factory that PublicationContractWriter.write() wraps in a hardcoded `List.of(EssayPublicationContract.kind())`. site/src/content.config.ts already defines a second real blog content type — blogNote (contentType:'note', sharing publicBaseFields/translationFields/editorialFields with blogEssay, plus optional observation/model/boundary/experiment fields, no required structured body) — that the exporter cannot yet admit, prepare, approve, or release, because every seam assumes essay is the only kind. Per openspec/implementation-plan.md's S17a entry and its 'Shared refactoring rule', this slice both proves blog/note through the already-working prepare→approve→release path and performs the first justified refactor: extracting an immutable PublicationKind role plus a PublicationKinds collection that NoteIntake, the contract writer, and (per the 'Kind-neutral lifecycle rule') future public-link indexing all share, replacing NoteIntake's hardcoded EssayAdmission.Result with an AdmittedPublication.

**Constraints:**
- At most one new production boundary adapter — none is expected; kind selection is pure in-process dispatch over an existing, already-proven prepare/approve/release path
- No generic schema/reflection framework, no speculative cross-kind inheritance — PublicationKind is a role each kind implements directly (essay and note), selected by (collection, contentType) key via PublicationKinds' deterministic lookup
- NoteIntake.admit() must return an AdmittedPublication, not a concrete kind result type, and take the same PublicationKinds instance the contract writer uses
- Do not generalize beyond what essay+note evidence requires — do not add fields, body-section machinery, or hooks for book/album/concept/editorial kinds this slice
- In-memory acceptance subset stays well under the 1s slice budget
- The existing blog/essay path (all prior slice acceptance tests) must keep passing unchanged after the refactor

**Acceptance:** One blog/note fixture note (contentType 'note', all shared blogShared fields, no structured body required) is admitted, prepared into an RU+EN candidate pair, approved as an approved snapshot, and released into site output through the same handlers/CLI commands already proven for blog/essay — with no change to blog/essay's observable behaviour (its full existing acceptance suite stays green). Admission for both kinds routes through a shared PublicationKind role + PublicationKinds registry (deterministic (collection, contentType) lookup, unsupported-kind diagnostics, sorted contract enumeration) instead of EssayAdmission's hardcoded constants. NoteIntake.admit() returns an AdmittedPublication carrying whichever kind matched. write-publication-contract emits entries for both blog/essay and blog/note, each independently correct.

## 2. Decision

**Selected:** PublicationKind/PublicationKinds seam extracted from EssayAdmission; NotePublicationKind added; blog/note proven through admit→prepare→approve→release

**Selection policy:** Follow openspec/implementation-plan.md's S17a slice exactly: prove blog/note through the already-working essay path while performing the one justified refactor (PublicationKind role + PublicationKinds registry) inside the same red-green-refactor cycle, per the plan's own Shared refactoring rule and Kind-neutral lifecycle rule.

**Why selected:** Implemented via superpowers:subagent-driven-development with every implementer and reviewer dispatched as a Codex Companion Task (Spark for mechanical transcription, Luna for integration/judgment work, Terra for per-task reviews, Sol at xhigh effort for the final whole-branch review), per this project's established SDD-via-Codex convention. Five tasks: (1) extracted PublicationKind (role interface: collection/contentType/routePrefix/admit/contract), AdmittedPublication (kind-neutral admission carrier), and PublicationKinds (deterministic lookup + sorted contract enumeration) from the essay-only EssayAdmission/EssayPublicationContract, behaviour-preserving; (2) threaded PublicationKinds/NoteIntake through real constructor injection into all 6 handlers and their 5 CLI Command composition roots, replacing inline construction; (3) wrote a failing (RED) blog/note acceptance test; (4) added NotePublicationKind (same field contract as essay: identity + title + description, no required structured body, matching site/src/content.config.ts's blogNote schema) and turned the test GREEN; (5) closed PCM-02/PCM-03/ADM-06 coverage gaps (frontmatter projection, note-route link resolution, contract conformance for both kinds). Each task's implementer was followed by 4 parallel Codex reviewers (spec compliance, code quality, applying-sbpp, oo-design-heuristics); every Important/Critical finding was either fixed in a scoped fix round with a scoped re-review, or adjudicated by the controller with a recorded ruling. The final whole-branch review (gpt-5.6-sol, xhigh effort) caught a genuine cross-task gap the per-task reviews structurally could not see — the acceptance test stopped short of the release step the proposal/design/ProblemCard all promised — fixed and re-verified before archiving. Main specs (publication-admission, public-content-model) synced with the new blog/note scenarios and a corrected ADM-06 (contract now describes both installed kinds, dropped its stale EssayAdmission reference).


**Invariants:**
- blog/essay's admit→prepare→approve→release behaviour is unchanged (verified: full pre-existing acceptance suite green throughout)
- No new production boundary adapter was introduced this slice
- No new Jackson-serialized type was introduced without reflect-config.json registration (verified: none needed)

## 3. Rationale

**Counterargument:** One could argue the collision risk should have blocked S17a's own completion until fixed, since silent data collision is a serious class of bug. It was not treated as blocking here because: (a) it requires an author to independently choose the exact same publicId for both an essay and a note, which does not occur anywhere in the current vault; (b) fixing it properly means either a cross-kind uniqueness invariant or a path-layout migration for already-approved essay data — real architectural work that deserves its own design pass, not a rushed patch inside an already-large fix wave; (c) explicitly tracking it as prob-20260811-0b8b9f2d with a hard requirement to resolve before S17b keeps it visible and gated rather than silently deferred.

**Selected variant weakest link:** Every real filesystem adapter (FilesystemCandidateWorkspace, FilesystemApprovedSnapshotWorkspace, FilesystemReleaseOutputStore, FilesystemManagedSiteInstaller) keys its on-disk path by (collection, publicId) only, never contentType. This was unreachable before S17a (only blog/essay existed); now that blog/note shares the "blog" collection, a blog/essay/{slug} and a blog/note/{slug} could silently collide on disk. The final review surfaced this as real and load-bearing; the operator elected to track it as its own problem (prob-20260811-0b8b9f2d) rather than rush a fix into this slice's already-large final-review fix wave, since it must be resolved before S17b (blog/claim) adds a third kind sharing the same collection.
