# Configurable TranslationCommand strategy, defaulting to exporter-java's exact Codex invocation

## 1. Problem Frame

**Signal:** openspec/implementation-plan.md lists G3 (production worker protocol, cancellation, timeout, result carrier; tests remain worker-neutral) as a decision gate required before S03, and no Haft decision addresses it yet. S03's `prepare` command needs a real TranslationWorker adapter to produce the EN half of its first candidate.

**Constraints:**
- Reuse exporter-java's evidenced CodexRunner command as the default for now (operator instruction).
- The command must be configurable, not hard-coded into the Worker itself — the operator intends to swap in gemini/agy later (operator instruction).
- Tests must remain worker-neutral per the plan's own gate wording.

**Acceptance:** A recorded Haft decision states the production translation-worker protocol (process shape, timeout/cancellation, result carrier) with a concrete, evidenced default, before design.md for S03 (prob-20260804-97ecd928) is finalized.

## 2. Decision

**Selected:** Configurable TranslationCommand strategy, defaulting to exporter-java's exact Codex invocation

**Selection policy:** Operator explicitly instructed: reuse exporter-java's evidenced Codex command for now, but the command must be configurable rather than hard-coded into the Worker.

**Why selected:** Closes plan gate G3: production translation-worker protocol is a synchronous external process invocation, evidenced 1:1 from exporter-java's CodexRunner (`codex exec --ephemeral --sandbox workspace-write --skip-git-repo-check -C <workdir> --output-last-message <workdir>/agent-message.txt <prompt>`, no stdin, bounded timeout with forced termination on expiry, result read from `<workdir>/candidate.en.md`). TranslationWorker itself stays a minimal String-in/String-out port; ProcessTranslationWorker delegates argv construction to an injected TranslationCommand strategy so a future gemini/agy tool is a new implementation, not a rewrite. Tests remain worker-neutral — the in-memory fake never touches TranslationCommand or process management.


**Invariants:**
- ProcessTranslationWorker never constructs an argv list itself — it always delegates to an injected TranslationCommand.
- The result carrier is always a file named candidate.en.md inside the process's workdir; a missing file after the process exits (or a non-zero exit, or timeout) is always translation_failed, never a partial/best-effort result.

**Spec sections:**
- translation-preparation

**Post-conditions:**
- [ ] A real ProcessTranslationWorker configured with CodexTranslationCommand, run against a valid RU body and a live codex CLI, installs a non-empty EN body read from candidate.en.md.

## 3. Rationale

**Counterargument:** A fully declarative, config-file-driven command template (with placeholder substitution for workdir/prompt) would let the command be swapped without a code change at all, not just a new Java class. Rejected for S03 as speculative machinery with only one real consumer (Codex) so far; revisit once a second real tool is actually wired.

**Selected variant weakest link:** The result-file convention (candidate.en.md written into the workdir) is enforced only by the prompt text handed to whichever CLI is configured; a differently-behaving tool that ignores it fails closed as a generic translation_failed rather than a tool-specific diagnostic.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Configurable TranslationCommand strategy, defaulting to exporter-java's exact Codex invocation | **Selected** | Closes plan gate G3: production translation-worker protoc... |
| V2-hardcoded-codex | Rejected | Directly contradicts the operator's explicit instruction that the command must be configurable, not hard-coded into the Worker itself; would also require rewriting ProcessTranslationWorker to add a second tool later instead of adding one new TranslationCommand implementation. |

## 4. Consequences

**Rollback plan:**
Triggers:
- The workdir-file result convention proves unworkable for a second real tool
Steps:
1. Extend the port (not just the adapter) to let TranslationCommand also declare how to read back its result, inside S08's or a later slice's own red-green-refactor cycle.
Blast radius: publication-exporter translation-worker adapter only — the TranslationWorker port's String-in/String-out contract is unaffected

**Refresh triggers:**
- A second real TranslationCommand (gemini, agy, or other) is actually wired in, testing whether the fixed workdir-file result convention still holds across tools.
- S08 (TRP-03/04) introduces job isolation and concurrent-job handling that may require the workdir/result-file convention to carry more identity (job ID, source fingerprint) than this slice needs.
