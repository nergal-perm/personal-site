# Select Codex or Antigravity with exporter-root TOML and environment override

## 1. Problem Frame

**Signal:** `prepare` hard-wires the existing Codex command even though its
worker already delegates process argv construction through `TranslationCommand`.
The operator needs most translations to use the installed Antigravity `agy`
CLI, with a visible persistent switch back to Codex and no binary rebuild or
new bridge argument.

**Constraints:**
- Selection is exporter configuration, not a CLI argument or plugin setting.
- `publication-exporter.toml` lives in the exporter root (the process working
  directory supplied by the plugin); a non-blank environment variable has
  higher precedence.
- The only valid engine names are `codex` and `antigravity`; missing
  configuration defaults to `codex`.
- Configuration or selected-engine failures fail as `translation_failed`; they
  never silently invoke the other engine.
- Each CLI uses its own installed skills. No skill synchronization, copying, or
  agent-installation work belongs here.
- Existing job workspace, prompt, timeout, result-file contract, and bridge
  schema remain unchanged.

**Acceptance:** A user changes `[translation].engine` in the exporter-root
TOML file (or sets the one-run environment override) and the next `prepare`
run invokes only the selected command. Both commands use the existing isolated
job workspace and result-file contract. The README explains configuration,
precedence, default, and failure behavior.

## 2. Decision

**Selected:** V1-root-file-env-override — exporter-root TOML with environment
override.

**Selection policy:** Prefer the smallest operator-visible configuration that
works under the current Obsidian process model, preserves the existing worker
boundary, and permits a temporary override without changing bridge arguments.

**Why selected:** The plugin already starts the exporter with its working root
as `cwd`, so a local TOML file is stable for the normal GUI path and naturally
co-locates with review and job workspaces. The environment override gives a
temporary switch for diagnosis. A two-case factory realizes the configuration
without turning arbitrary executable templates into a new safety surface.

**Invariants:**
- A `prepare` run invokes exactly one configured engine.
- The configuration resolver never changes a TranslationWorker's job
  isolation, prompt, timeout, or three required result files.
- `antigravity` means the installed `agy` CLI using its own skills; the exporter
  does not materialize, copy, or validate those skills.
- Invalid configuration or an unavailable selected CLI is visible as
  `translation_failed`, never fallback success from the other engine.

**Admissibility:**
- NOT: No bridge schema/argument, plugin setting, engine-specific prompt, model
  parameter, executable-path, automatic retry, or per-note selection.
- NOT: No generic configuration framework or arbitrary command-template
  interpreter.

## 3. Rationale

**Counterargument:** An environment-only setting removes the need for a parser,
and a plugin setting would be easier to discover in Obsidian. Environment-only
configuration is opaque and unreliable for GUI launches; a plugin setting
would create an unnecessary cross-process contract for a backend-only choice.

**Selected variant weakest link:** The working-directory file convention is
simple but direct CLI invocations outside the configured exporter root will use
the default unless the environment override is supplied. This is acceptable for
the single-operator plugin path and must be documented plainly.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| V1 exporter-root TOML + environment override | **Selected** | Persistent and visible for the plugin path, with one-run override and no bridge change. |
| V2 environment only | Rejected | GUI environment inheritance is opaque; it does not preserve a visible persistent choice. |
| V3 plugin setting | Rejected | Couples a worker concern to plugin deployment and needs a new bridge surface. |

**Evidence requirements:**
- Command-selection tests cover default, TOML selection, environment precedence,
  invalid configuration, and the two argv shapes.
- The full publication-exporter suite and native-image build stay green.
- One real Antigravity `prepare` run writes the expected three result files and
  returns a schema-v2 success response.

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| The configured engine is selected without a binary rebuild or bridge argument. | Command-selection tests and a restart of the same native executable after changing the TOML file. | Both `codex` and `antigravity` selections produce only their corresponding argv. |
| An invalid or unavailable selection does not publish a mixed or fallback candidate. | `prepare --json` failure test. | `translation_failed`, no successful candidate installation, and no invocation of the other command. |

## 4. Consequences

**Rollback plan:**
Triggers:
- The `agy` CLI cannot honor the existing job-workspace/result-file protocol.
- The local working-directory file proves unreliable for the real plugin path.
Steps:
1. Set the TOML engine to `codex` or remove the file to return to the preserved
   Codex default.
2. Reopen this decision with the observed Antigravity protocol failure or
   configuration-location evidence before adding a new engine surface.
Blast radius: command selection/configuration, documentation, and tests only;
no approved snapshot, release output, site content, or plugin setting requires
migration.

**Refresh triggers:**
- A third translation engine is requested.
- The plugin stops setting a stable exporter-root working directory.
- An operator needs per-note selection, custom model/effort parameters, or
  agent-skill management.
