# Semantic/site-acceptance RU normalization depth

## 1. Problem Frame

**Signal:** S02 (closed, prob-20260804-60dfda6c) made `inspect-publication` report real identity and four independently-absent state dimensions for a valid `blog/essay`, but every one of those dimensions is hard-coded absent — there is still no command that produces a candidate. Per openspec/implementation-plan.md's S03 entry, the exporter needs a `prepare` command that, for the S02 essay, creates exactly one coherent first-publication candidate triple (normalized RU, worker-produced EN, and an empty valid references.json) and returns schema-v2 `ready_for_review`, without touching approved or site state. This is also where two plan-level decision gates land: G3 (production translation worker protocol, cancellation, timeout, result carrier — tests must stay worker-neutral) and G4 (semantic/site-acceptance vs byte-for-byte legacy compatibility depth for the RU normalization this slice performs) are both listed as required 'before S03' and are not yet decided (haft_query status shows no G3/G4 decision).

**Constraints:**
- Introduces at most one new production boundary adapter per the plan's slice discipline (condition 4); if the acceptance boundary genuinely needs both a worker adapter and a candidate-workspace adapter, that tension must be resolved explicitly in design.md, not silently.
- No candidate replacement, incremental diff (TRP-02/03), job isolation (TRP-04), semantic occurrence IDs (TRP-05/SEM-02), links/assets/protected-Markdown (PCM-03/04/05, S12-S14), or concurrent-job handling in this slice — those fail closed as unsupported state.
- exporter-java remains a read-only compatibility oracle (evidence), never a code donor.
- Governed by /nullables, /applying-sbpp, and /oo-design-guide for all new code, per the standing project convention (memory feedback-exporter-design-testing-conventions).
- Outside-in TDD discipline per implementation-plan.md: failing acceptance test first, in-memory fakes before real adapters, unit tests only for genuinely combinatorial logic.

**Acceptance:** `publication-exporter prepare --json` for the S02-admitted valid essay creates one candidate workspace holding RU (normalized source), worker-produced EN, and an empty valid `references.json`, and returns a schema-v2 response with `ok: true`, `status: "ready_for_review"`; approved-snapshot and release/site state are provably untouched. Preparing an unrelated invalid publication does not create a job or candidate for it (ADM-05). The essay's manifest entry carries only PCM-01/PCM-02-projected fields for this slice's scope. G3 and G4 are each closed with a recorded Haft decision before design.md is finalized. All new acceptance/unit tests plus the full existing 84-test publication-exporter suite stay green; the in-memory acceptance subset stays under 1 second per the plan's slice discipline.

## 2. Decision

**Selected:** Semantic/site-acceptance RU normalization depth

**Selection policy:** Prefer the variant that satisfies this slice's acceptance without importing undecided legacy compatibility scope; operator confirmed via AskUserQuestion before scoring.

**Why selected:** RU candidate body is the frontmatter-stripped source body passed through verbatim for a plain, linkless, assetless essay. No attempt to reproduce exporter-java's byte-level quirks. This closes plan gate G4 for S03: matches the plan's explicit non-goal ('preserving known defects') and its framing of exporter-java as behavioural evidence, not a design template. Operator confirmed this direction over AskUserQuestion during the functional collaborative-design pass.


**Invariants:**
- RU normalization depends only on the admitted note's frontmatter-stripped body text — no dependency on legacy exporter-java internals or output format.

**Spec sections:**
- public-content-model
- translation-preparation

**Post-conditions:**
- [ ] RU candidate body for a plain essay (no links/assets/comments) is byte-identical to its source body after frontmatter removal.

## 3. Rationale

**Counterargument:** A future slice could need byte-stable RU output for some downstream tool (e.g. a diff cache keyed by exact bytes); if that need materializes, S08 has to decide whether to renormalize existing candidates or accept the discontinuity.

**Selected variant weakest link:** If S08's approved-vs-candidate diffing (TRP-02) later proves sensitive to exact whitespace/line-ending choices made here, this slice's pass-through normalization may need revisiting.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| Semantic/site-acceptance RU normalization depth | **Selected** | RU candidate body is the frontmatter-stripped source body... |
| V2-byte-for-byte | Rejected | Requires reverse-engineering and locking in undocumented legacy whitespace/line-ending quirks before any real consumer needs byte-level comparability — contradicts the plan's non-goal list and its stop-and-split rule against building for a guessed future need. |
