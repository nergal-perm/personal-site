# PrepareHandler mirrors the approved snapshot into CandidateWorkspace before short-circuiting when RU is unchanged

## 1. Problem Frame

**Signal:** With engine = antigravity in the live exporter-root configuration, Obsidian's Prepare for publication command returns immediately and presents a completed English translation even though no English draft was produced.

**Constraints:**
- Read-only investigation only — no fixes.
- Do not invoke a real translation against a vault note without explicit operator approval.

**Acceptance:** Identify, with reproducible evidence, whether the false completion originates in agy invocation/output behavior, Java bridge result handling, or plugin response interpretation; do not modify production code during diagnosis.

## 2. Decision

**Selected:** PrepareHandler mirrors the approved snapshot into CandidateWorkspace before short-circuiting when RU is unchanged

**Selection policy:** Root-cause fix confirming V1: keep the existing no-op-on-unchanged-RU optimization (avoid pointless re-translation cost, especially relevant now that translation can be routed through a real Antigravity/Codex process), but close the correctness gap V1 exposed — the short-circuit must guarantee a candidate actually exists before claiming ready_for_review, not just that the approved baseline is unchanged.

**Why selected:** approvedRussianSourceIsUnchanged only ever consulted ApprovedSnapshotWorkspace; it never checked CandidateWorkspace. When an approved snapshot exists with RU text matching the current source but no candidate directory exists (candidate cleared, never created, or a fresh review-workspace state), prepare() returned ok=true/ready_for_review with nothing for the plugin to open — the literal defect in the problem title. Fix: matchingApprovedBaseline(...) (renamed from approvedRussianSourceIsUnchanged) now returns the matched approved CandidateSnapshot instead of a boolean; ensureCandidateMirrorsApproved(...) installs that snapshot into CandidateWorkspace only if candidateWorkspace.find(identity) is empty, using the existing CandidateWorkspace.install(...) contract already proven by S03/S05. No translation worker invocation is added or removed — the optimization's cost-avoidance property is preserved exactly.


**Invariants:**
- The approved-unchanged short-circuit never returns BridgeResponse.prepared unless CandidateWorkspace actually has a readable candidate for the identity afterward.
- Mirroring an approved snapshot into CandidateWorkspace never invokes translationWorker.
- ensureCandidateMirrorsApproved is a no-op (does not overwrite) when a candidate already exists for the identity.

**Admissibility:**
- NOT: NOT: does not change behavior for the already-covered case (candidate present, RU unchanged) — same response as before
- NOT: NOT: does not address V3's plugin-side observability gap (distinguishing freshly-translated from reused/mirrored) — separate, smaller follow-up if desired
- NOT: NOT: does not change TRP-02's diff-scope semantics or S08/S09 replacement/recovery paths

## 3. Rationale

**Counterargument:** A reviewer could argue prepare() shouldn't silently write to CandidateWorkspace at all inside what is nominally a read-only short-circuit branch — mutating state on what looks like a fast/no-op path is a surprising side effect, and a caller who only wanted to check status (not mutate anything) now triggers a filesystem write. This is a real cost: it slightly widens what "just checking if prepare would be a no-op" means. It's accepted here because prepare() has never been a read-only/idempotent-query operation — every branch (translated, stale, translation_failed) already writes workflow status and/or installs a candidate — so mirroring the approved snapshot into the candidate on this branch is consistent with, not a departure from, prepare()'s existing contract as a command that leaves the review workspace in a state matching its response.

**Selected variant weakest link:** ensureCandidateMirrorsApproved uses candidateWorkspace.find(identity) (existence-only, ru.md+en.md presence) rather than read(identity) to decide whether to mirror — consistent with S04's established convention (dec-20260805-s04-...) that find() is the cheap readiness check, but it means a partially-corrupted candidate directory that still passes find()'s existence check would not be repaired by this fix. That gap is the same pre-existing, deliberately-deferred one S04's decision record already named (partial-candidate-directory handling belongs to S09-scope hardening, not here).

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| PrepareHandler mirrors the approved snapshot into CandidateWorkspace before short-circuiting when RU is unchanged | **Selected** | approvedRussianSourceIsUnchanged only ever consulted Appr... |
| Fall through to the normal translate-and-install path whenever the candidate is missing, treating 'no candidate' the same as 'source changed' | Rejected | Would re-invoke the translation worker even though RU content is byte-identical to what was already approved and previously translated successfully — wasteful, and defeats TRP-02's diff-based scope-narrowing intent (and the exact cost this decision's constraint set out to avoid under the newly-configurable Antigravity/Codex engine). |
| Change BridgeResponse.prepared's shape/status to flag 'reused, not freshly translated' without touching CandidateWorkspace | Rejected | Only addresses V3 (observability/provenance) and leaves the actual defect unfixed: with no candidate on disk, the response would still be lying about there being an English draft to review, regardless of how honestly it labels the source of that (nonexistent) draft. |
