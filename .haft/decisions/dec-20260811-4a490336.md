# write-publication-manifest aggregates NoteIntake.admit(...) over a now-deterministically-sorted VaultReader.listPublishCandidates(), reporting every selected note's outcome instead of silently excluding failures

## 1. Problem Frame

**Signal:** VaultReader.listPublishCandidates() (publication-exporter/src/main/java/dev/eugene/publicationexporter/vault/VaultReader.java) already discovers Boolean-publish=true notes and NoteIntake.admit(...) already validates one note end-to-end, and RefreshPublicationQueueHandler already iterates listPublishCandidates() per-note — but every existing aggregate consumer (refresh-publication-queue) silently treats an inadmissible note as EXCLUDED and moves on. No command exists that reports a note-scoped operation's real ADM-05 "whole-vault manifest" guarantee: that an aggregate operation either blocks or surfaces every invalid selected note's diagnostics, never silently omitting one from a manifest that looks complete. The real FilesystemVaultReader.listPublishCandidates() also has no proven ordering or ignored-path contract (Files.walk's traversal order is not guaranteed sorted, and there is no dedicated test proving a note inside a normally-git/tool-ignored path like a dotfolder is still discovered) — both are prerequisites for a whole-vault listing an authoring tool could trust.

**Constraints:**
- At most one new production boundary adapter this slice — the real discovery adapter is FilesystemVaultReader as it already exists, hardened with an ordering/ignored-path contract, not a wholly new class, unless acceptance-test evidence proves otherwise
- No queue-state mutation — this command must not write workflow status or any other persisted state
- No release of a partially valid vault — aggregate release itself is out of scope, only the discovery/admission manifest that a future release slice would consume
- In-memory acceptance subset stays well under the 1s slice budget

**Acceptance:** A new read-only whole-vault command lists every Boolean-selected note exactly once, excludes publish-flag lookalikes (absent/false/string "true"), includes selected notes in normally-ignored vault paths, and — if any selected note fails admission — the command's result is not a manifest that silently omits that note: it is blocked or otherwise makes every failing note's diagnostics explicit, per ADM-05's "Whole-vault release is requested" scenario. The real discovery adapter has an explicit, tested ordering contract (deterministic, not incidental to filesystem traversal order) and an explicit, tested ignored-path contract (a selected note under a dotfolder or other normally-tool-ignored path is discovered). Queue-state mutation (refresh-publication-queue's job) and actually releasing a partially-valid vault remain out of scope.

## 2. Decision

**Selected:** write-publication-manifest aggregates NoteIntake.admit(...) over a now-deterministically-sorted VaultReader.listPublishCandidates(), reporting every selected note's outcome instead of silently excluding failures

**Selection policy:** Resolve the functional shape via collaborative-design first (command naming, response shape, standalone-vs-BridgeResponse — settled by strong precedent from S15/S06, no fresh ask needed), settle the technical shape via a second collaborative-design pass identifying the deterministic-order fix and confirming zero new adapters, then implement task-by-task with independent spec/quality/SBPP/OO-design review after each task and one whole-branch review at the end; any Important/Critical finding either gets fixed (dispatched at the security tier when security-relevant) or is explicitly parked with a documented ruling the final review re-triages, never silently dropped.

**Why selected:** Reusing NoteIntake.admit(...) (already proven by every note-scoped command) and VaultReader.listPublishCandidates() (already proven by refresh-publication-queue) meant this slice added zero new admission logic and zero new production adapters — only a deterministic-order fix to an existing method and a thin aggregation layer over already-trusted collaborators. PublicationManifest/ManifestEntry follow the S15/S06 precedent of a standalone, non-BridgeResponse result type for a CLI-only, list-shaped response, avoiding another case added to the BridgeResponse wide-DTO problem already under Haft review (prob-20260808-08cf74cd). The ordering fix was necessary regardless of this slice's own goals: NullVaultReader's Map.copyOf(...) never actually guaranteed order (a standing note, note-20260808-d1ce9a1a, had already flagged this), and FilesystemVaultReader's Files.walk(...) order is filesystem-dependent — both needed to be pinned down for a whole-vault manifest to be trustworthy at all.


**Invariants:**
- No selected note is ever silently dropped from the manifest — every entry in vaultReader.listPublishCandidates() produces exactly one ManifestEntry, admitted or blocked.
- PublicationManifest.ok() is always derived from entries, never settable independently — an invalid (ok=true but a blocked entry present) manifest cannot be constructed.
- write-publication-manifest never writes candidate, approved, workflow, or release state — it is read-only.
- PublicationManifest/ManifestEntry are never wrapped in BridgeResponse or exposed through bridge-contract/schema-v2.json's conformance surface.
- listPublishCandidates() returns results in deterministic, sorted-by-vault-relative-path order from both VaultReader implementations.
- FilesystemVaultReader's publish-flag content read is always performed through the confinement-validated real path, never a separately re-derived original path.

**Post-conditions:**
- [ ] `write-publication-manifest --vault <path>` returns exit code 0 with `ok:true` when every selected note admits, or exit code 1 with `ok:false` and every failing note's diagnostics when any selected note is invalid.

## 3. Rationale

**Counterargument:** The strongest case against this design is that PublicationManifestHandler.manifest() and ManifestEntry/PublicationManifest's constructors were all flagged (Important + 2 Minor) by the applying-sbpp per-task review for mixing abstraction levels / doing inline validation rather than extracting named helper methods. The controller parked all three findings on the grounds that they match this codebase's own established conventions exactly (RefreshPublicationQueueHandler's orchestration shape; every existing value type's inline requireNonNull/List.copyOf pattern) — a reasonable but contestable judgment call, since a stricter reading of Composed Method would still prefer further decomposition regardless of precedent.

**Selected variant weakest link:** FilesystemVaultReader's now-fixed TOCTOU gap (commit 36dc92e) still has an inherent, unavoidable residual window between real-path resolution and file open, explicitly accepted per this project's documented threat model (single local user exporting their own vault). If that threat model ever changes (multi-tenant use, untrusted concurrent vault writers), this and every sibling filesystem adapter using the same pattern would need re-examination together, not just this one class.

**Evidence requirements:**
- Full mvn -q -o test suite green (555/555) after every task and after the final-review security fix.
- Final whole-branch review (gpt-5.6-sol, xhigh) confirmed the CLI→handler→sorted-adapter→NoteIntake chain preserves order and drops no invalid note, confirmed zero BridgeResponse/schema-v2 coupling, confirmed reflect-config.json accessor names match real @JsonProperty methods, and confirmed no candidate/approved/workflow/release writes anywhere in the call chain.

## 4. Consequences

**Rollback plan:**
Triggers:
- A future whole-vault release slice (consuming this manifest as its precondition) finds the PublicationManifest/ManifestEntry shape insufficient and needs a structural change.
- The FilesystemVaultReader threat-model assumption (single local user, no concurrent adversarial writes) is revisited and found insufficient.
Steps:
1. Revert the five S16 commits (c018f54, c733fff, 5638d67, aab2557, 7c19f5c) plus the security fix (36dc92e).
2. No data migration needed — the command is stateless and read-only; no persisted artifact depends on the manifest's shape.
Blast radius: publication-exporter's vault package (ordering fix), a new manifest package, one CLI command, one native-image config file. No effect on prepare/approve/release/site/refresh-publication-queue command behaviour.
