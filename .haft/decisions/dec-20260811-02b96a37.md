# Fail-closed cross-kind (collection, publicId) collision guard added to FilesystemCandidateWorkspace and FilesystemManagedSiteInstaller, using each adapter's own already-persisted identity carrier

## 1. Problem Frame

**Signal:** Every real filesystem adapter in publication-exporter keys its on-disk path by (publicCollection, publicId) only, never publicContentType: FilesystemCandidateWorkspace (candidate/FilesystemCandidateWorkspace.java:167-169, resolves `{collection}/{publicId}/candidate`), FilesystemApprovedSnapshotWorkspace (approved/FilesystemApprovedSnapshotWorkspace.java:445-447, `{collection}/{publicId}/approved`), FilesystemReleaseOutputStore (release/FilesystemReleaseOutputStore.java:54-58, `{collection}/{publicId}/release`), and FilesystemManagedSiteInstaller (site/FilesystemManagedSiteInstaller.java:383-386, `src/content/{collection}/{locale}/{publicId}.md`). PublicationIdentity's own equality (bridge/PublicationIdentity.java) is (collection, contentType, publicId) — so two admitted publications of different kinds sharing the same collection and publicId are treated as distinct by admission, but resolve to the identical real path in all four adapters. This was unreachable before S17a because blog/essay was the only kind ever admitted into the "blog" collection; S17a (prob-20260811-ab6a410a) added blog/note as a second real kind sharing that same collection, making the collision reachable for the first time: a `blog/essay/foo` and a `blog/note/foo` would silently overwrite each other's candidate, approved snapshot, release output, and site-content file. PublicationManifestHandler (manifest/PublicationManifestHandler.java, the ADM-05 whole-vault handler) performs no cross-note duplicate-identity detection at all, for any kind pair, so nothing in the current system would surface this before the collision actually happens on disk. S17a's final whole-branch review (gpt-5.6-sol, xhigh effort) surfaced this; the operator elected to track it as its own problem rather than patch it inside S17a's fix wave, since S17b-S17f (openspec/implementation-plan.md's remaining content-kind ladder) will all share the "blog" collection too and are equally exposed.

**Constraints:**
- Must not require re-laying-out the on-disk structure of already-approved/released essay data without a safe migration path — any fix touching real adapter paths needs to handle publications that already exist under the current (collection, publicId)-only layout
- Should not require a new production boundary adapter merely to add a check — prefer extending an existing adapter/handler's own invariant over introducing new I/O surface
- Must resolve before S17b (blog/claim) lands, since claim shares the "blog" collection with both essay and note and would be exposed to the identical collision the moment it exists

**Acceptance:** A decision or slice exists that either (a) makes (collection, publicId) uniqueness an enforced invariant across kinds at admission or install time (fail closed on a second kind claiming an already-used publicId within the same collection), or (b) extends the real adapters' addressing to include contentType with an explicit, evidence-based migration story for already-approved essay data. Either way, a reproduced fixture proving a blog/essay/{slug} and a blog/note/{slug} no longer silently collide on disk is part of the acceptance evidence.

## 2. Decision

**Selected:** Fail-closed cross-kind (collection, publicId) collision guard added to FilesystemCandidateWorkspace and FilesystemManagedSiteInstaller, using each adapter's own already-persisted identity carrier

**Selection policy:** Prefer extending each vulnerable adapter's own existing invariant using data it already persists, per the problem's constraint against introducing a new production boundary adapter, a new on-disk marker file, or any change to the existing on-disk layout for already-approved/released essay data.

**Why selected:** Reproduction showed only two of the four adapters were actually vulnerable: FilesystemCandidateWorkspace silently overwrote the essay's candidate with the note's, and FilesystemManagedSiteInstaller silently overwrote the essay's site markdown. FilesystemApprovedSnapshotWorkspace was already safe: install() unconditionally calls recoverIfNeeded(identity, true), which reads any existing approved directory's references.json and validates its stored PublicationIdentity against the incoming one, throwing ApprovedSnapshotIntegrityException on mismatch before any write. FilesystemReleaseOutputStore was already safe for an unrelated reason: install() is create-only and throws ReleaseAlreadyExistsException whenever the release directory already exists, regardless of identity. Both vulnerable adapters already persist a full identity carrier at the exact path being overwritten: FilesystemCandidateWorkspace writes references.json (containing the full PublicationIdentity) into every candidate directory it creates, and FilesystemManagedSiteInstaller writes a contentType frontmatter line into every markdown file it installs. Reading that already-written carrier back before replacing the destination, and comparing it to the incoming identity, required no new adapter, no new marker file, and no change to the existing on-disk layout; same-kind reprepare/reinstall (the legitimate S08/S10 replace-in-place paths) still matches identity and proceeds normally, only a genuine cross-kind mismatch throws (CandidateWorkspaceKindCollisionException, ManagedSiteKindCollisionException). Verified with CrossKindAddressCollisionAcceptanceTest (4 tests against the real adapters, no mocks): an essay's candidate, approved snapshot, release output, and site content all survive an attempted note install at the identical (blog, same-slug) address. Full suite: mvn test, 576/576 passing, BUILD SUCCESS, no regressions.


**Invariants:**
- blog/essay's and blog/note's existing admit->prepare->approve->release behaviour is unchanged (verified: full pre-existing acceptance suite green throughout)
- No new production boundary adapter was introduced
- No change to the existing on-disk layout for candidate, approved, release, or site content

## 3. Rationale

**Counterargument:** A global uniqueness registry enforced at admission time (PublicationManifestHandler/NoteIntake) would catch a collision before any adapter write and would not depend on each adapter's own carrier format. It was rejected because it would require either a new production boundary adapter (a persistent cross-note identity index) or running whole-vault discovery before every single-note prepare/mark-reviewed/build-from-review invocation, which the CLI does not currently do and which the problem's constraints explicitly discouraged (no new I/O surface merely to add a check).

**Selected variant weakest link:** The guard only fires when an existing destination contains a fully-written, readable identity carrier (references.json for candidate, a contentType frontmatter line for site). A destination left in a partially-written or corrupted state from an unrelated failure is treated as absent and the write proceeds; this matches each adapter's existing recovery-tolerant behaviour elsewhere and is not a new gap, but it means the guard is not a substitute for a vault-wide uniqueness check if one is ever needed.

| Variant | Verdict | Reason |
|---------|---------|--------|
| Fail-closed cross-kind (collection, publicId) collision guard added to FilesystemCandidateWorkspace and FilesystemManagedSiteInstaller, using each adapter's own already-persisted identity carrier | **Selected** | Reproduction showed only two of the four adapters were ac... |
| Global uniqueness registry enforced at admission time (PublicationManifestHandler/NoteIntake) | Rejected | Requires either a new production boundary adapter or running whole-vault discovery before every single-note command, which the constraints explicitly discouraged. |
| Sidecar (collection, publicId) -> contentType marker file introduced at each adapter's shared parent directory | Rejected | Rejected once reproduction showed both vulnerable adapters already persist an equivalent identity carrier in the exact file they write (references.json, frontmatter contentType); a new marker file would duplicate that information and add a second on-disk artifact per adapter for no additional safety. |
| Extend real adapter addressing to include contentType, with a migration story for already-approved essay data | Rejected | No real deployed instance of the exporter has installed any approved/release/site data yet, so there is no existing data to migrate; changing the on-disk layout now would be pure speculative rework against the problem's own preference to preserve the current layout. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| S17b (blog/claim) can add its kind without editing FilesystemCandidateWorkspace or FilesystemManagedSiteInstaller's new collision checks. | S17b's implementation diff touches neither CandidateWorkspaceKindCollisionException nor ManagedSiteKindCollisionException nor their call sites in FilesystemCandidateWorkspace.java / FilesystemManagedSiteInstaller.java. | No edits to those four files beyond the pre-existing PublicationKinds.installed() registration line. |

## 4. Consequences

**Rollback plan:**
Triggers:
- The new collision checks reject a legitimate same-kind reprepare or reinstall
- A future kind slice needs a destination layout the identity-carrier read cannot parse
Steps:
1. git revert the commit introducing CandidateWorkspaceKindCollisionException/ManagedSiteKindCollisionException and their call sites
2. Re-open prob-20260811-0b8b9f2d
Blast radius: publication-exporter's candidate and site adapter packages only; no persisted data or migration involved
