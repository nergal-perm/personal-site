# refresh-publication-queue: shared WorkflowStateClassifier + WorkflowStatusEditor port reconcile truthful workflow state

## 1. Problem Frame

**Signal:** The exporter has four working bridge commands (prepare, inspect-publication, mark-reviewed, build-from-review, install-to-site) but no refresh-publication-queue: Main.java's subcommands list does not include it, and no frontmatter workflow scalar is ever persisted back to a source note anywhere in the codebase (grep for workflow/publication_status/status_ keys in src/main returns nothing). InspectPublicationHandler and BridgeResponse already compute and return the six-state vocabulary (metadata_blocked, ready_for_review, translation_failed, ready_to_publish, stale — translating not yet observed anywhere) live, per-note, on demand, but nothing writes that classification back to disk or reconciles it across a set of tracked publications. BRG-01's refresh clause, BRG-05, and BRG-06 (workflow-bridge/spec.md) and TRP-06 (translation-preparation/spec.md) are already fully specified with scenarios, which is evidence this is primarily a realization slice — but that must be confirmed via the functional collaborative-design pass, not assumed. S08's PrepareHandler holds an in-process ReentrantLock keyed by PublicationIdentity only for the duration of one synchronous prepare() call, so it does not by itself give a later, separate refresh process any durable signal that a translation is active; how refresh detects 'actively translating' needs a technical design decision, not a guess.

**Constraints:**
- No unrelated frontmatter normalization or whole-file YAML rewriting — implementation-plan.md explicitly excludes this from S11
- At most one new production boundary adapter (implementation-plan.md slice rule) — a guarded exporter-owned frontmatter workflow-scalar editor; reuse the existing Frontmatter/FrontmatterScalar parser rather than introducing a new YAML engine
- Reuse the six-state classification already computed by InspectPublicationHandler/BridgeResponse rather than reinventing a second classifier that could disagree with inspect-publication for the same observation window (BRG-05's 'same command, same state' scenario)
- Queue refresh scans publication candidates already known to the exporter, not a whole-vault discovery pass — ADM-01/whole-vault discovery is S16's job, not this slice's
- Do not touch prepare, inspect-publication, mark-reviewed, build-from-review, or install-to-site business logic itself
- In-memory acceptance test subset first (decisive/uncertain/translating vault fixtures), then the same contract against the real frontmatter editor for byte/permission preservation

**Acceptance:** refresh-publication-queue reports updated/unchanged/uncertain counts across the six-state workflow vocabulary and updates only stale exporter-owned workflow scalar fields via a guarded atomic replacement that preserves all other source bytes and file permissions. A note whose persisted workflow scalar decisively disagrees with its unambiguous current artefact state is corrected and counted as updated. A note under an active, valid translation lock is left untouched (workflow state and job ownership not overwritten) and does not count as updated. A note whose source changed concurrently since validation, or whose workflow keys are duplicate/aliased/malformed, blocks the update without rewriting the source and is counted as uncertain rather than guessed. All existing acceptance/unit tests remain green plus new S11 acceptance coverage: an in-memory vault with decisive, uncertain, and translating fixtures proves the reconciliation contract, then the identical contract runs against the real frontmatter editor.

## 2. Decision

**Selected:** refresh-publication-queue: shared WorkflowStateClassifier + WorkflowStatusEditor port reconcile truthful workflow state

**Selection policy:** Prefer the option that reuses this codebase's already-proven ports/patterns (Frontmatter's retained-source parsing, PrepareHandler's sourceStillMatches hash-guard shape, the existing create/createNull adapter-factory convention) over introducing a new abstraction, and that makes cross-command disagreement structurally impossible rather than merely tested against — per implementation-plan.md's one-adapter-per-slice discipline and this project's own outside-in TDD process (every option was screened by whether it passed its own failing acceptance test first, then whether the final whole-branch review's cross-task composition check accepted it).

**Why selected:** A single WorkflowStateClassifier (pure function, six-plus-one state vocabulary) is called by both InspectPublicationHandler and the new RefreshPublicationQueueHandler, so the two commands cannot disagree on classification by construction (BRG-05). A new WorkflowStatusEditor port + Filesystem/Null adapter pair gives an atomic, byte-preserving, hash-guarded write for the single exporter-owned workflowStatus scalar, reusing PrepareHandler.sourceStillMatches()'s proven re-validate-before-commit shape and Frontmatter's existing parse/retained-source machinery rather than inventing new I/O primitives. PrepareHandler gained purely additive workflowStatus writes on its three existing exit paths (no new branching), making translation_failed and stale durably reconstructable for the first time. VaultReader.listPublishCandidates() is a cheap frontmatter-only pre-filter reusing the existing Frontmatter.parse(...).flag("publish") call, avoiding a second discovery mechanism.


**Invariants:**
- InspectPublicationHandler and RefreshPublicationQueueHandler always classify identical evidence identically, because both call the same WorkflowStateClassifier.classify(...).
- WorkflowStatusEditor.write(...) only mutates the single workflowStatus scalar and only when the note's current content hash matches the caller's validated expectation; every other byte of the note is preserved.
- A blocked or failed workflow-status write never changes what prepare/refresh itself returns to the caller — it is best-effort bookkeeping, not part of either command's success contract.

**Admissibility:**
- NOT: Must not change the live release/build/site-installation state — this slice is workflow-state observation and reconciliation only.
- NOT: Must not silently collapse metadata_blocked/uncertain/absent into a guessed decisive state.
- NOT: Must not require a new production adapter beyond WorkflowStatusEditor (implementation-plan.md's one-adapter-per-slice discipline).

## 3. Rationale

**Counterargument:** The final whole-branch review's own findings are the strongest case against this decision as shipped: a single shared classifier only prevents disagreement if every call site actually threads the same evidence into it, and one call site (InspectPublicationHandler's no-candidate branch) initially did not — passing Optional.empty() instead of the admitted note's persisted scalar, silently defeating BRG-05's guarantee until caught. That the architecture is sound didn't stop an incomplete wiring of it from shipping past nine per-task reviews; only the final cross-cutting review caught it. This means the shared-classifier pattern's safety property is real but not self-enforcing — it depends on every future call site remembering to thread persisted evidence through, which nothing in the type system currently guards against.

**Selected variant weakest link:** Two narrow, non-load-bearing races were found by the final whole-branch review's fix-wave and its own scoped re-review, then deliberately parked rather than fixed in a third round: (1) RefreshPublicationQueueHandler's UNCHANGED shortcut skips the guarded-write hash check within the narrow window between NoteIntake.admit()'s read and the classification decision (note-20260808-65b44134); (2) PrepareHandler's stale-branch re-read can throw an uncaught IllegalStateException if frontmatter is corrupted specifically during an in-flight translation (note-20260808-4bb7c4a3). Both require adversarial timing to trigger and cause no persisted-state corruption if they do — worst case is an uncaught exception or a missed reconciliation, not data loss.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| refresh-publication-queue: shared WorkflowStateClassifier + WorkflowStatusEditor port reconcile truthful workflow state | **Selected** | A single WorkflowStateClassifier (pure function, six-plus... |
| Separate classification logic duplicated in InspectPublicationHandler and RefreshPublicationQueueHandler | Rejected | Would let the two commands drift on edge cases — exactly the class of bug the final whole-branch review caught (an early implementation of InspectPublicationHandler's no-candidate branch passed Optional.empty() instead of threading the persisted scalar through, silently defeating BRG-05's same-state guarantee until the final review's fix wave caught it). |
| Whole-file YAML parse-and-rewrite for persisting workflowStatus | Rejected | Would rewrite every line through a YAML serializer, losing user formatting, comments, and line-ending conventions on every write — unacceptable for a scalar that gets rewritten on every prepare/refresh of a note a human is actively editing. Chose Frontmatter.withScalarSet's byte-offset surgical splice instead (parse once, retain original source, replace only the value span of the target line). |
| Active translation-lock detection via a new identity-scoped job marker for BRG-06's 'translating' state | Rejected | PrepareHandler is fully synchronous and never writes to the source note while translation is running, so BRG-06's translating-lock scenario is satisfied by construction, not by detection — building real detection would require a new cross-process job marker keyed by PublicationIdentity that nothing in this codebase currently provides (TranslationJob.id() is an anonymous UUID with no such link). Documented as a scope pin, not implemented speculatively. |

**Evidence requirements:**
- Full publication-exporter test suite stays green with a strictly higher count than the pre-slice baseline (420 → 461).
- obsidian-plugin test suite passes with updated fixtures matching the real schema-v2 queueRefreshed shape (74 tests, 73 pass, 1 environment-specific skip).
- Every requirement scenario (BRG-01 refresh clause, BRG-04 new scenario, BRG-05, BRG-06, TRP-06) traced to a specific covering test, per tasks.md Task 10.2.

## 4. Consequences

**Rollback plan:**
Triggers:
- refresh-publication-queue corrupts or mis-writes workflowStatus scalars in a real vault after deployment
- The obsidian-plugin refresh integration breaks against a real Obsidian install despite passing its own test suite
Steps:
1. git revert the range from 76b81d4 (S11's opening commit) through the final fix-wave commits (f7ce96e, 8662093) on master
2. Re-run the full publication-exporter and obsidian-plugin test suites to confirm the revert lands cleanly
3. Re-open prob-20260808-726e0e91 (or a fresh problem) with the concrete failure evidence before re-attempting the slice
Blast radius: Vault note frontmatter (workflowStatus scalar only, via WorkflowStatusEditor's byte-preserving write), the refresh-publication-queue CLI command and its obsidian-plugin wiring (main.js, bridge-client.js), and InspectPublicationHandler's classification of the no-candidate branch. No release/site/candidate/approved-snapshot state is touched by this slice.

**Refresh triggers:**
- A future slice adds occurrence/semantic-link state to the workflow vocabulary, which may require re-examining WorkflowStateClassifier's fixed six-plus-one enum.
- G6 (legacy cutover) is decided and migration touches notes with persisted workflowStatus scalars from the pre-S11 era.
