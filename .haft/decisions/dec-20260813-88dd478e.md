# G7 — Freeze the current nine-page-type editorial grammar as one contract edition; implement only `about` in S17f

## 1. Problem Frame

**Signal:** PublicationKinds.installed() does not register editorial/curated_page; the exporter cannot admit, prepare, approve, or release any curated editorial page, so legacy exporter-java's EditorialParser remains the only path currently able to produce site/src/data/pages/*.json.

**Constraints:**
- Minimal-slice discipline per implementation-plan.md: 1-3 new OpenSpec scenarios, at most one new production boundary adapter, in-memory acceptance subset under 1 second, no foundation-only/refactor-only milestone.
- Must not decide G7 quietly through incidental code — record it as an explicit Haft decision before or during design.
- Must reuse the existing PublicationKind/PublicationKinds/AdmittedPublication seam from S17a; no new generic schema framework or speculative cross-kind abstraction.
- Release artifact shape for curated pages may differ from ordinary Markdown release (JSON page data) only if this slice's fixture actually needs it — do not redesign essay/note/claim/book/concept/album release paths.
- Whole prior acceptance suite (763 tests as of baseline) must stay green throughout.

**Acceptance:** A recorded G7 decision exists (grammar frozen as one edition or versioned independently); an OpenSpec change (proposal, spec, design, tasks) documents the slice; one curated-page fixture completes prepare -> approve -> release through the CLI, producing a valid JSON page release artifact; write-publication-contract includes editorial/curated_page's kind-specific rules; the whole prior acceptance suite stays green; the final whole-branch review (Codex, GPT 5.6 Sol, max effort) passes with no unresolved Important/Critical findings.

## 2. Decision

**Selected:** G7 — Freeze the current nine-page-type editorial grammar as one contract edition; implement only `about` in S17f

**Selection policy:** Prefer the option matching the implementation plan's own minimal-slice discipline (1-3 new scenarios, one adapter, in-memory acceptance under one second) and its explicit note that existing implementation is behavioural evidence, not a template to be redesigned without cause.

**Why selected:** The current nine-page-type grammar is treated as one frozen contract edition, not independently versioned per page type: any future page-type implementation must match the shape already proven by exporter-java's EditorialParser rather than being redesigned ad hoc. Within that frozen edition, S17f implements admission, translation validation, and JSON-artifact release for exactly one page type (about) end-to-end, proven by one acceptance fixture. The remaining eight page types are named in the kind's contract as future editorialPage values and explicitly rejected for now with a "not yet supported" diagnostic, rather than silently admitted with the wrong shape.


**Invariants:**
- Only editorialPage: about is admitted as editorial/curated_page in this exporter edition; the other eight legacy page keys are named but rejected with a diagnostic.
- The frozen grammar edition is a single edition across all nine page types; no page type gets its own contract version number.

## 3. Rationale

**Counterargument:** One could argue freezing now is premature since only one of nine page types has been implemented against it — the 'edition' is mostly aspirational until more page types are proven.

**Selected variant weakest link:** If a future page type (e.g. home, with its card-grid grammar) turns out to need a materially different admission/projection shape than about, the 'one frozen edition' framing will need revisiting rather than mechanically extending the about pattern.

**Rejected alternatives:**
| Variant | Verdict | Reason |
|---------|---------|--------|
| G7 — Freeze the current nine-page-type editorial grammar as one contract edition; implement only `about` in S17f | **Selected** | The current nine-page-type grammar is treated as one froz... |
| Version each of the nine page-type grammars independently | Rejected | No evidence anywhere in the codebase or site of any page-type grammar changing independently of the others; all nine were authored together in one legacy tool and the live site consumes them uniformly. Independent versioning adds a mechanism with no current justification. |
| Implement all nine page types in S17f | Rejected | Violates the plan's minimal-slice discipline (1-3 new scenarios, one adapter, in-memory acceptance under 1 second); each page type has a materially different body grammar, so this would be nine kinds' worth of admission logic in one commit. |

**Predictions:**
| Claim | Observable | Threshold |
|-------|------------|-----------|
| The about page type's release JSON artifact stays field-compatible with the legacy exporter-java shape (id, type, language, title, summary, eyebrow, lead, principles, colophon, topics, links, searchable, sourceLanguage, sourceHash, translationStatus), embedded inline rather than split into a companion release-provenance.json. | site/src/data/pages/ru/about.json and site/src/data/pages/en/about.json produced by the new exporter parse with the same keys/shapes as the file already on disk today. | byte-equivalent JSON keys and value shapes for the about fixture |

## 4. Consequences

**Rollback plan:**
Triggers:
- A second page type's acceptance fixture proves the frozen-edition framing wrong (materially incompatible shape).
Steps:
1. Revert this decision's binding scope to per-page-type versioning.
2. Re-open G7 with the new page type's evidence.
Blast radius: Only the editorial/curated_page kind's own admission/projection code; no other kind is affected.
