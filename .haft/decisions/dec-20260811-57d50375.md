# Implement PCM-05 as AssetResolver + VaultAssetReader (Null/Filesystem) + CandidateAsset, materialized atomically into FilesystemCandidateWorkspace's staged install

## 1. Problem Frame

**Signal:** LinkResolver (publication-exporter/src/main/java/.../prepare/LinkResolver.java) already classifies an embed target as asset-like by extension (ASSET_EXTENSIONS) but explicitly leaves it untouched: `appendLink` does `output.append(link.group())` and returns without blocking, verbatim-copying the raw `![[image.png]]` Obsidian embed syntax into the normalized candidate body. PCM-05 (openspec/specs/public-content-model/spec.md) requires the exporter to resolve referenced publishable assets within the vault (preferring an exact vault-relative match over a unique basename fallback), reject ambiguous/unsafe (traversal/symlink-escaping) targets before any candidate replacement, and materialize each accepted asset under a deterministic content-derived (hash) name so identical bytes referenced more than once collapse to one public asset. None of this exists yet: VaultReader (vault/VaultReader.java) exposes only readSource/exists/listPublishCandidates for note text — no binary asset read capability — and CandidateWorkspace (candidate/CandidateWorkspace.java) has no notion of installing an asset alongside RU/EN bodies. exporter-java's AssetResolver (astroexport/assets/AssetResolver.java) was read as behavioural evidence only (compatibility oracle, not a code donor): SHA-256 content-addressing, exact-path-before-basename-fallback, ambiguous-basename rejection, traversal/symlink/hidden-path escape rejection, and byte-identical dedup with suffix-family consistency checking.

**Constraints:**
- At most one new production boundary adapter: asset byte reading + content-addressed materialization.
- No asset variants, optimization, remote assets, or media types beyond the existing ASSET_EXTENSIONS set (png/jpg/jpeg/gif/svg/webp/mp3/mp4).
- In-process acceptance subset stays below one second.
- One to three new OpenSpec scenarios targeted (PCM-05's three baselined scenarios).
- exporter-java remains a read-only compatibility oracle, never a code donor.
- No candidate/approved/release state change in one unreviewable step.

**Acceptance:** Preparing an essay with one image emits one content-addressed asset and rewrites the candidate reference to point at it; an ambiguous basename match or an escaping/unsafe target (traversal, symlink) blocks preparation with an asset diagnostic before any candidate replacement; identical asset bytes referenced more than once materialize as exactly one deterministic public asset with all references pointing at it. In-memory asset bytes prove the behaviour first; a real vault/file adapter then passes the same exact-path, ambiguous-basename, deduplication, and escape contracts.

## 2. Decision

**Selected:** Implement PCM-05 as AssetResolver + VaultAssetReader (Null/Filesystem) + CandidateAsset, materialized atomically into FilesystemCandidateWorkspace's staged install

**Selection policy:** The plan's own outside-in slicing discipline (openspec/implementation-plan.md): in-memory acceptance-first, one real adapter proven against the same contract, at most one new production I/O boundary adapter this slice, governed by OpenSpec's collaborative-design + tasks.md sequence and verified via subagent-driven-development's per-task 4-way review plus a final max-effort whole-branch review before archiving.

**Why selected:** Followed the OpenSpec-governed 8-task low-level plan built from proposal.md/design.md's collaborative-design passes. Implemented via subagent-driven-development with Codex Companion Task implementers (model tier by complexity: Spark for mechanical tasks, Luna/Terra for medium integration work, Sol for the security-sensitive real filesystem adapter and path-confinement fix) and a 4-way review (spec compliance, code quality, applying-sbpp, oo-design-heuristics) per task, followed by a max-effort whole-branch review and one fix wave before archiving.


**Invariants:**
- No candidate/approved/release state is mutated by an unreviewable step
- exporter-java remains read-only evidence, never a code donor
- bridge-contract/schema-v2.json and obsidian-plugin/ remain untouched (confirmed unchanged by the final review)

## 3. Rationale

**Counterargument:** A rigorous critic would say: shipping a known-bypassable security-adjacent check, even a low-priority one, sets a precedent that "good enough" review outcomes get archived rather than fully closed, and the fix (parsing actual Markdown link destinations instead of regex substring-diffing) is well-understood and not enormous in scope — it could have been attempted as a fourth round instead of parked.

**Selected variant weakest link:** EnglishCandidateValidator's asset-route-preservation regex check (guards PCM-06) remains bypassable by deliberately adversarial translation-worker output (IPv6-literal and schemeless protocol-relative URLs specifically crafted to survive both the negative-lookbehind and external-URL-stripping defenses) after 3 rounds of review finding successive bypasses. Parked as documented residual risk (note-20260811-ac1db940) rather than fixed with a 4th regex patch, since the realistic threat model here (an accidentally-mangling translation worker) is already well-covered, and this project has an existing standing decision (dec-20260807-s08-translation-worker-trust-boundary-8bab0bc6) trusting the same-UID translation worker process, making the adversarial-output threat model this residual defends against already out of scope elsewhere in the codebase.
