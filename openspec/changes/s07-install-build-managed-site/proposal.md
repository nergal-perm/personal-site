## Why

S06 (`dec-20260806-s06-materialize-approved-essay-7671c117`) gave the exporter a `build-from-review` command that reads a durable approved snapshot and writes one RU essay, one EN essay, and deterministic minimum release provenance into a brand-new, review-root-scoped output directory (`<outputRoot>/<collection>/<id>/release/`). That intermediate artifact is not what S07 installs. Nothing yet moves the *approved publication itself* into the site's actual managed content roots or proves an Astro build succeeds from it. The site already carries a pre-existing, exporter-independent contract this install must satisfy: `site/scripts/check-content.mjs` verifies a `.astro-export/release-provenance.json` manifest (`schemaVersion`, `selectedPages`, `managedTrees`, `managedFiles`, `activationCount`, `deactivationCount`, `payloadDigest`) hashed over three managed trees — `public/assets/vault`, `src/content`, `src/data/pages` — plus a required-page-contract check (`about`, `concepts`, `essays`, `home`, `library`, `music`, `notes`, `search`, `claims` must exist in both locales) that S06's per-publication output does not produce on its own. S07 is the next slice in `openspec/implementation-plan.md`: install the approved publication into previously-absent managed site roots, pass the existing gate, and complete a real Astro build — without touching any code-owned site file. **Architectural note, confirmed during the technical collaborative-design pass (see `design.md` Context point 5) and re-affirmed after the final whole-branch review questioned it:** `install-to-site` reads `ApprovedSnapshotWorkspace` directly, the same source S06 itself reads — it does not chain through S06's `build-from-review`/`ReleaseOutputStore` output. REL-01 already establishes that release materialization derives authority exclusively from the approved snapshot; S06 and S07 are two independent, siblings realizations of that same authority, not a pipeline where one depends on the other's artifact. `ReleaseOutputStore`, `ReleaseProvenance`, and `BuildFromReviewHandler` remain fully untouched by this slice. Milestone A (S01–S07) cannot close without a real Astro build from a real publication. Governed by Haft problem `prob-20260806-e95236b1` under the slice-sequence decision `dec-20260803-76166a5e`.

## What Changes

- Add a site-install step that, given the approved snapshot for one publication (the same `ApprovedSnapshotWorkspace` source S06's `build-from-review` independently reads — not S06's `ReleaseOutputStore` artifact; see the architectural note above), writes its RU/EN essay files into `src/content/<collection>/<lang>/<id>.md` and writes a site-level `.astro-export/release-provenance.json` manifest — computed the same way `site/scripts/check-content.mjs` and `site/tests/release-provenance.test.mjs` already compute and verify it (SHA-256 over each managed tree via the existing kind/length/relative-path/payload digest scheme, plus per-file `managedFiles` hashes and a canonical `payloadDigest`) — into a previously-absent (or previously-empty) set of managed site roots (REL-04, REL-05, REL-06).
- Introduce exactly one new production boundary adapter for this install step, following S05/S06's established shape: a small port proven first against an in-memory managed-tree fake, then a real filesystem adapter proven against the same contract.
- **Close a real requirement gap surfaced by this slice, not synthesized around it:** `site/src/content.config.ts`'s Astro schema requires non-empty `title`/`description` on every essay entry, but neither field exists anywhere in the current pipeline — `EssayAdmission` (S02/ADM-02) admits only `publish`, `publicId`, `publicCollection`, `publicContentType`, `sourceId`, and no requirement in `openspec/requirements-baseline.md` mentions "title" or "description" at all. These are vault-author-provided fields (the Obsidian plugin gates on their presence before allowing "Prepare to publication"), so this slice extends `EssayAdmission` to admit them from source frontmatter (ADM-04), threads them through `CandidateSnapshot`/`ApprovedSnapshotWorkspace` alongside the existing RU/EN bodies, extends the translation-worker contract (TRP-01) to translate title/description the same way it already translates the body, so the approved snapshot this slice's install step reads carries the resulting RU/EN pairs alongside the existing bodies. `ReleaseProvenance` and the S06 release output are untouched — see the architectural note above. This widens the code surface across S02/S03/S05/S06's already-shipped types, but not their requirement scenarios: PCM-01, PCM-02, TRP-01, REL-01, and REL-03 are already worded generically enough ("normalized fields defined for its publication kind," "candidate workspace") to cover two more admitted string fields by construction — confirmed, not assumed, in the functional collaborative-design pass. Only ADM-04 needs new scenario text, since its existing illustrative field list never mentions essay at all.
- The install blocks before writing anything if declared release inputs (the approved snapshot itself) are not stable/valid at commit time — trivially true for a first-ever install into empty roots, but the guard exists so REL-04's general shape is exercised, not assumed.
- The install writes only inside the three declared managed roots and never touches any other site path (config, templates, layouts, other collections' pre-existing content) — proven by a fixture that asserts non-managed content is byte-identical before and after.
- The exporter's production code never shells out to Node/npm/Astro — it only ever writes managed-tree content and the manifest. Verifying `astro build` and `check-content.mjs` actually accept that output is the job of one slow smoke test (test code only), which subprocess-invokes both. The required-page-contract's curated pages (`about`, `home`, etc.) are pre-seeded fixture data for this smoke test, not exporter-generated output — no requirement in this slice's scope (`ADM-06`/S15, S17f) produces curated pages, so generating them is out of bounds here.

**Explicitly excluded from this change** (per the S07 slice boundary in the implementation plan): replacing an existing live-site generation and recovering from an interrupted replacement — both are S10 (`REL-04`'s "input changes concurrently" scenario and `REL-05`'s replace/recover scenarios stay unexercised until then). Also excluded: assets, links, multiple publications in one invocation, and any new content kind — those are S13/S14/S16/S17.

## Capabilities

### New Capabilities

None — this slice realizes requirements already fully specified in the baseline (`release-materialization`); it does not introduce a new capability area.

### Modified Capabilities

- `release-materialization`: REL-05 gains a new "Empty-destination install" scenario — its existing "Staged site content is valid" scenario and its siblings ("Staged content or filesystem is unsafe," "Installation is interrupted") all presuppose a prior generation to replace, protect, or recover to, which S07's first-ever install does not have. REL-04 and REL-06 are realized, not modified — their existing scenario text already reads correctly for a first install without presupposing any prior generation (scope pins).
- `publication-admission`: ADM-04's "Kind-specific contract is complete"/"incomplete" scenarios currently illustrate required fields for book, album, concept, and editorial-page kinds but never mention essay. This slice adds essay's title/description requirement to that list — a genuine gap this slice is the first to need closed, not a pre-existing pin.

`public-content-model` (PCM-01, PCM-02), `translation-preparation` (TRP-01), and `release-materialization` (REL-01, REL-03) are realized, not modified, by threading title/description through the pipeline: each is already worded generically enough ("normalized fields defined for its publication kind," "candidate workspace," "public content reflects the approved snapshot") to cover two more admitted string fields by construction, once ADM-04 declares them as part of essay's kind contract. See `scope-pins.md` for the full record.

## Impact

- **Modified:** `publication-exporter/` — a new `install-to-site` command and its one new production adapter (`ManagedSiteInstaller`: in-memory fake + real filesystem adapter), a `SiteReleaseManifest` value type matching `check-content.mjs`'s exact hashing/canonicalization scheme, `EssayAdmission`/`NoteIntake` admitting title/description, `CandidateSnapshot` widening to carry them (shared by `CandidateWorkspace` and `ApprovedSnapshotWorkspace`), and the translation-worker contract widening to translate them alongside the body. `prepare`'s observable behavior is unchanged beyond admitting/translating two more fields end to end (see `design.md` D3/D4). **`inspect-publication` and `mark-reviewed` gained real observable behavior changes in a post-review fix, not just internal plumbing:** the metadata-integrity fix (closing a review-visibility/tamper-integrity gap the first final-whole-branch review found) widened `ReferenceMap` to six hashes, extended `mark-reviewed`'s staleness check so a source, RU-candidate, or EN-candidate title/description change now blocks approval the same way a body change already did (previously such a change would have gone undetected and approval would have proceeded), and added four new top-level fields (`ruTitle`/`enTitle`/`ruDescription`/`enDescription`) to `inspect-publication`'s `ReviewPlan` response — schema-safe via `additionalProperties: true`, but a genuine response-shape change, not internal-only. `build-from-review`, `ReleaseOutputStore`, and `ReleaseProvenance` are fully untouched — `install-to-site` reads `ApprovedSnapshotWorkspace` directly, independent of S06's release-output path (`design.md`'s Context, point 5).
- **Read-only integration target:** `site/` — `site/scripts/check-content.mjs` and `astro build` are exercised as-is by the real-adapter contract test and the one slow smoke test, both test code; production code never invokes Node/npm/Astro. No `site/` source file is modified by this change. Test fixtures under a temporary directory (not the live `site/src/content`) stand in for the managed roots during acceptance and smoke testing.
- **Untouched:** `exporter-java/` (read-only compatibility oracle), `obsidian-plugin/` (no bridge-response surface is introduced — `install-to-site` is not in `bridge-contract/schema-v2.json`'s command enum and is not consumed by the plugin; the plugin's own "Prepare to publication" title/description pre-check is a separate, coordinated but out-of-scope change in that codebase), vault content, candidate store, approved-snapshot store, and deployment.
- **Governance:** implements Haft problem `prob-20260806-e95236b1`, under decision `dec-20260803-76166a5e` (slice sequence).
