## Context

`publication-exporter` releases one publication per `BuildFromReviewHandler.buildFromReview(PublicationIdentity identity)` call (not a batch) — `approvedSnapshotWorkspace.read(identity)` fetches that one `CandidateSnapshot`, and `releaseOutputStore.install(identity, approved.ruBody(), approved.enBody(), provenance)` writes it straight through with zero transformation. Today, link resolution happens once, eagerly, at prepare time: `LinkResolver.appendLink()` (prepare/LinkResolver.java:55-86) bakes `[label](route)` into the body immediately if `PublicNoteIndex.routeFor()` finds the target currently *admitted* in the vault, or a permanent bare `label` if not — this is admission-time knowledge, not approval-time knowledge, and it is frozen forever once the referrer is approved. `ReferenceMap.occurrences()` (reference/ReferenceMap.java) already persists `Occurrence(id, order, targetSourceId, ruLabel, enLabel)` per S19, with no span/position field (S19 deliberately dropped position info — only the transient prepare-time `LinkOccurrence` carries `spanStart`/`spanEnd`) — but nothing downstream of `PrepareHandler.previousOccurrencesFor()` (used only for positional ID reuse across re-prepares) ever reads it. `ReleaseProvenance.activationCount()`/`deactivationCount()` are hardcoded stubs (`SiteReleaseManifest`'s same-named fields are a separate, whole-site-tree-hash concept — `computeOver()` never sees an individual publication or its occurrences — and stay out of scope for this slice). `InstallToSiteHandler.installToSite()` (installtosite/InstallToSiteHandler.java:29-44) independently reads the same approved snapshot and passes it straight into `managedSiteInstaller.installWithOutcome(identity, planned)`, which `PublicationKind.projectManagedArtifact()` ultimately renders from `approved.ruBody()`/`enBody()` verbatim — so today's eager route-baking (and, once this slice lands, an unresolved `ref:` marker) reaches the actually-published site exactly as approved, with no separate resolution step. No approved snapshot durably records its own stable source ID today — approved storage is keyed entirely by `PublicationIdentity` (`ApprovedSnapshotWorkspace.read(PublicationIdentity)`), so there is currently no way, without touching the vault (forbidden for release per REL-01), to answer "which approved snapshot, if any, currently has source ID X" — which is exactly what resolving `Occurrence.targetSourceId()` at release time requires.

## Goals / Non-Goals

**Goals:**
- `LinkResolver` emits a durable, release-resolvable marker (`[label](ref:<targetSourceId>)`) for unambiguous admitted non-embed link targets, instead of eagerly baking a route or a permanent label. Embeds, private/unresolved/ambiguous targets, and asset embeds are entirely unchanged (PCM-03's narrowed scope).
- Approved snapshots durably record their own stable source ID; `ApprovedSnapshotWorkspace` gains a source-ID lookup capability usable without touching the vault.
- A new release-time step, invoked from `BuildFromReviewHandler` before `ReleaseOutputStore.install()`, resolves every `ref:` marker in the approved body against the *current* state of its target's approved snapshot (if any) — substituting a kind-correct, locale-prefixed route + the occurrence's stored label when the target is currently approved, or stripping to the stored plain label when it is not — without ever mutating the approved snapshot itself.
- `ReleaseProvenance` computes real `activationCount`/`deactivationCount` by comparing this release's resolved occurrence states against the prior release's recorded provenance.
- `InstallToSiteHandler` applies the same resolution (registry + resolver) to the snapshot it hands to `ManagedSiteInstaller`, so the managed site tree never contains a literal `ref:` marker.

**Non-Goals:**
- No change to `MarkReviewedHandler`, candidate installation, or approval locking.
- No batch/multi-publication release orchestration — this design works within the existing one-`PublicationIdentity`-per-call model.
- No migration or automatic rewriting of any approved referrer (S21-S23's concern).
- No change to embed/transclusion resolution, asset resolution (PCM-05), or the private/unresolved/ambiguous label path.
- No change to `SiteReleaseManifest`'s `activationCount`/`deactivationCount`/`selectedPages` stubs — a separate, whole-site-tree-hash aggregate concept that never sees an individual publication's occurrences; a future slice's concern.

## Decisions

**Decision: `[label](ref:<targetSourceId>)` marker format, reusing exporter-java's validated convention.**
The legacy `exporter-java` oracle already solved exactly this problem with a `](ref:<id>)` markdown-link-shaped marker (`SemanticReferenceMarkdown`'s `\]\(ref:[^)]+\)` pattern), later substituted with a real route or stripped at release time. Reusing the *shape* (not the code — `exporter-java` stays a read-only oracle, nothing is imported from it) means: it round-trips safely through Markdown tooling (it looks like an ordinary link during any intermediate processing), it's trivially locatable by regex without any stored position data, and it's a scenario-tested precedent rather than a novel invention. Alternative considered: extend `OccurrenceLabelMarkers`' Private-Use-Area delimiter scheme to survive into the persisted body — rejected because that scheme is explicitly transient-only (stripped before installation, per S19's design), and PUA characters surviving into a persisted, git-tracked Markdown file is a worse operational property than a `ref:` URL that reads as ordinary (if unresolved-looking) Markdown.

**Decision: `PublicNoteIndex` gains a parallel `sourceIdFor(target)` lookup, populated in its existing single vault scan; `LinkResolver.appendLink()` changes only its "target is currently admitted, non-embed" branch.**
`LinkResolver.resolve()` runs *before* `VaultSourceIdentityIndex` is ever constructed today (`PrepareHandler.prepareAfterIdentityCheck`, line 118-123, builds it lazily and only when `occurrences` is non-empty) — so `LinkResolver` cannot reach into that index for a target's stable source ID without a real pipeline reordering. But `PublicNoteIndex.from()` (prepare/PublicNoteIndex.java:22-31) already visits every admitted candidate exactly once via `noteIntake.admit(candidate, vaultReader)`, and `AdmittedPublication.sourceId()` (already populated at admission — e.g. `EssayPublicationKind.admit()`, from the frontmatter `id` field) is already sitting right there in `registerIfAdmitted` at zero extra vault I/O cost. So `PublicNoteIndex` gains a second parallel map (`sourceIdsByFilenameStem`, alongside the existing `routesByFilenameStem`), populated in the same scan, with a new `sourceIdFor(String linkTarget): Optional<String>` accessor — and the same `ambiguousStems` removal that already protects `routeFor` (line 29: `ambiguousStems.forEach(routes::remove)`) is extended to remove from both maps, so an ambiguous target has neither a route nor a resolvable source ID, consistent with PCM-03's existing "ambiguous gets the same safe-label treatment as private" rule. This requires `NoteIntake.Result` to expose a one-line `sourceId()` forwarding to `admission.sourceId()` (intake/NoteIntake.java — trivial, `admission` already holds it), not a new resolution mechanism.

With that in place, `LinkResolver.appendLink()` changes only its "target is currently admitted, non-embed" branch (prepare/LinkResolver.java:66-76): instead of `output.append('[').append(label).append("](").append(route.get()).append(')')`, it emits `output.append('[').append(label).append("](ref:").append(knownNotes.sourceIdFor(target).orElseThrow()).append(')')` (the `orElseThrow` is safe — `sourceIdFor` and `routeFor` are populated from the exact same admitted-candidate set, so a present route always has a present source ID). The embed branch (`isEmbed` — line 62, 78) and the "not present" branch (line 81-85, private/unresolved/ambiguous) are untouched. `LinkOccurrence` continues to record `spanStart`/`spanEnd` around the *label* exactly as today (needed for translation-preservation via `OccurrenceLabelMarkers`, S19); the marker's `ref:` portion is new text added around the existing labeled span, not a replacement of the span-tracking mechanism.

**Decision: `ReferenceMap` gains its own `sourceId` field (not `CandidateSnapshot`); `ApprovedSnapshotWorkspace` gains `findBySourceId(String)`.**
`ReferenceMap` (reference/ReferenceMap.java) already carries this snapshot's own `PublicationIdentity` (`identity()`) and is already the type serialized to `references.json` (via `ReferenceMapCodec`) — it is the natural, already-existing home for "what is this candidate's own stable identity," not a new concern bolted onto `CandidateSnapshot` (which is purely body/fields content). `ReferenceMap` gains an `Optional<String> sourceId()` accessor alongside `identity()`, with `@JsonProperty("sourceId")` and `ReferenceMapCodec` read/write support (a small, well-understood extension — S19 already extended this exact class/codec pair for `occurrences`). 109 existing call sites across 25 files construct `ReferenceMap` via `.of(...)`/`.empty(...)` — to avoid rippling a mandatory new parameter through all of them, `sourceId` is added as a *new overload* (`ReferenceMap.of(identity, sourceId, ruHash, enHash, ruFieldsHash, enFieldsHash, structuredDataHash, occurrences)`, taking `String` directly — never-null at the call site, wrapped internally) alongside the existing 7-arg `.of(...)`/`.empty(...)` factories, which continue to work unchanged and internally default `sourceId` to `Optional.empty()`. Only `PrepareHandler.buildReferenceMap` (the one production call site that has a real source ID available) needs to move to the new overload; every existing test fixture keeps compiling against the old one untouched. The value comes from `PrepareHandler`'s already-computed `String sourceId = intake.frontmatterString("id").orElseThrow()` (prepare/PrepareHandler.java:81) — no new resolution logic, just threading an already-available value into `buildReferenceMap`'s existing `ReferenceMap.of(...)` call. This is the exact same identity space a referrer's `Occurrence.targetSourceId()` is drawn from (both originate from `VaultSourceIdentityIndex`/the note's own `id` frontmatter field), so they compare directly. `ApprovedSnapshotWorkspace.findBySourceId(String sourceId)` returns `Optional<CandidateSnapshot>` by scanning currently-approved snapshot directories, reading each one's `references.json`, and matching `referenceMap().sourceId()` — the same directory-scan pattern `FilesystemApprovedSnapshotWorkspace` already uses internally, just keyed differently. Alternative considered: a separate persisted `sourceId → PublicationIdentity` catalog, mirroring `exporter-java`'s `VaultReferenceCatalog` — rejected for this slice because it adds a new artifact type and a new consistency-maintenance burden (must stay reconciled against approved-snapshot state) for no benefit over storing the field directly on the snapshot that already needs to be read to answer the question; revisit only if a future slice needs source-ID lookup independent of approval state.

**Decision: two collaborators — `ApprovedTargetRegistry` (or similarly named lookup type) and a stateless `OccurrenceMarkerResolver` — not one combined class.**
`ApprovedTargetRegistry` is built once per `buildFromReview` call: for the one snapshot being released, collect its `ReferenceMap.occurrences()`' distinct `targetSourceId`s, call `findBySourceId` once per distinct ID, and hold the small resulting `{targetSourceId → (ruRoute, enRoute)}` map (routes built from the target's own `PublicationKind.routePrefix()` + `publicId` + language, per REL-02's kind-correct-route scenario) — targets with no current approved snapshot are simply absent from the map. `OccurrenceMarkerResolver` is a stateless utility (matching this codebase's existing style: `LinkResolver`, `OccurrenceLabelMarkers` are both stateless) taking `(body, registry, language)` and returning `(rewrittenBody, activatedCount, deactivatedCount)`: it regex-scans for `\]\(ref:([^)]+)\)`, and for each match either substitutes `](route)` (registry hit) or rewrites to the bare label with the marker removed (registry miss), using `ReferenceMap.occurrences()` to validate the found marker IDs match the recorded sequence (mirroring `exporter-java`'s `validateActivationSequence` precedent) before trusting the labels. Separating these lets registry construction (I/O-touching, needs `findBySourceId`) be tested independently from text substitution (pure function, easily table-tested with nullable body/registry fixtures) — this codebase's and `/nullables`' preferred shape over one class mixing I/O lookup with pure text transformation.

**Decision: activation/deactivation counts come from comparing this release's resolver output against the *prior* release's provenance, read back from `ReleaseOutputStore`.**
`BuildFromReviewHandler.releaseApprovedSnapshot()` already has access to whatever the previous release wrote (it must, to detect `ReleaseAlreadyExistsException`); reading the prior `release-provenance.json`'s recorded per-occurrence resolution state (which `ref:` IDs resolved to a route last time) and diffing against this run's `OccurrenceMarkerResolver` output gives `activationCount` (newly-resolved) and `deactivationCount` (newly-unresolved) directly, satisfying REL-03's "Same approved state is built twice → identical provenance" (no prior state, or identical state, → 0/0 deterministically) and "tampered" scenario (recorded counts become part of the tamper-detectable provenance payload, unchanged from today's hash-binding approach, just with real numbers instead of stubs).

## Risks / Trade-offs

- [Risk] `findBySourceId` scanning every approved-snapshot directory on every release is O(n) in total publication count, per release. → Mitigation: this codebase's existing scans (`FilesystemApprovedSnapshotWorkspace` internals, `PublicNoteIndex.from()`) are already O(n) over the vault/approved tree with no reported performance requirement contradicting it; revisit only if a real slice surfaces a performance requirement (none does today).
- [Risk] Changing `LinkResolver`'s baked-route branch could regress any existing test asserting a baked route in prepare-time output for an admitted target. → Mitigation: task list runs the full existing suite (863 tests) after this change specifically and expects PCM-03-scenario tests referencing the old baked-route assertion to need updating — these are internal test expectations, not a spec violation, per the PCM-03 delta already agreed.
- [Risk] A target's `sourceId` and a referrer's `targetSourceId` must be drawn from literally the same identity resolution to compare equal — any drift between how `VaultSourceIdentityIndex` assigns one versus the other silently breaks all resolution. → Mitigation: both are populated from the exact same `VaultSourceIdentityIndex` call site during prepare; task list includes an explicit acceptance test asserting a target's own recorded `sourceId` equals what a referrer's occurrence records as `targetSourceId` for that same target.
- [Risk] Marker substitution happening via regex directly on the approved Markdown body is fragile if a marker were to appear inside a code block or other protected region. → Mitigation: `LinkResolver` only ever emits the marker at true link positions (never inside protected regions — it already respects `ProtectedRegionScanner`), so a marker's mere presence in an approved body *is* proof it's a real occurrence; no separate protected-region rescan is needed at release time, only the occurrence-sequence validation against `ReferenceMap.occurrences()` already described above.
